What the course expects and what you'll be able to do

The idea

CS 551 teaches graphics theory and graphics programming side by side. The theory (vectors, matrices, transformations, lighting) hasn't changed much in decades. The hardware and the OpenGL API changed a lot, so Chen teaches the old theory on the modern shader-based OpenGL (W1 p.11).

The prerequisites tell you what math and programming he assumes. The outcomes list is what Quiz 1 asks about, so know which items are on it and which plausible-sounding ones aren't.

What to know

It's a 3-credit graduate course with prerequisites MATH 203, CS 310 and CS 367. It needs Java programming, vector analysis and matrix calculations, and it's taught in Java/JOGL (W1 p.3).

PrerequisiteWhat it covers (per Chen)

CS 310Java programming and data structures. The one non-Mason students most often lack (Lesson 1 video)
CS 367Computer systems and hardware (Lesson 1 video)

The five course outcomes (W1 p.4) are these.

  1. Implement OpenGL programs using Java/JOGL.
  2. Apply trigonometry, geometry, vector analysis and linear algebra to graphics problems.
  3. Utilize transformation and viewing for 3D animation.
  4. Utilize GPU shaders for vertex and pixel lighting.
  5. Describe advanced capabilities, including raytracing, blending, texture mapping, bump mapping, displacement mapping, geometry shader and shadows.

Course logistics from the video. Every lesson has a quiz, an assignment and a discussion. There are 14 or 15 quizzes, together about 20% of the grade, and each quiz can be taken three times. Assignments are about another 20%, and exams make up the rest. Homework and quiz for a lesson are due by the end of the following week, and he suggests taking the quiz before doing the homework because the quiz reviews the material (Lesson 1 video).

The toolchain. JDK, Eclipse, JOGL, OpenGL

The idea

Four pieces stack on each other. OpenGL is the graphics library that talks to the GPU. JOGL is a Java wrapper around it, so Java code can call OpenGL. The JDK is what compiles and runs Java. Eclipse is just the editor and build tool sitting on top.

JOGL has two halves. The .jar files hold the Java classes, and the native libraries (.dll on Windows) hold the platform code that actually reaches OpenGL. Both have to be wired into the project, which is what the setup slide is about.

Object, model, image, graphics library, primitive

The idea

There's a chain of three things. The object is the real or imaginary thing you want to show. The model is how the computer stores it, as vertices and colors. The image is the result on screen, a 2D grid of pixels. Graphics is the machinery that turns a model into an image.

You don't draw pixels yourself. You call a graphics library, a set of commands, and it only accepts very simple shapes called primitives. Anything complex, like an airplane, has to be broken into points, lines and triangles first.

What to know

A real or imaginary object is represented in a computer as a model and displayed as an image (W2 p.3).

A model is an abstract description of the object's shape (vertices) and attributes (colors). It's used to find all the points on the object that correspond to the pixels in the drawing area (W2 p.3). Models can also store positions and the hierarchical relationships of components (W2 p.14).

An image is simply a 2D array of pixels (W2 p.3). The application program controls "the pen" through a graphics library to produce it (W2 p.3).

A graphics library is a set of graphics commands or functions, bound in C, Java or other languages on different platforms, that specify primitive 2D and 3D models to be digitized and displayed (W2 p.4). OpenGL is the most widely used graphics library or API (W2 p.6). OpenGL is bound in C and JOGL puts Java on top (Lesson 2 video). DirectX includes the graphics library Direct3D, which Chen says is Windows-specific (W2 p.4, Lesson 2 video).

Primitives are simple shapes, namely points, lines and triangles (W2 p.4). At the bottom, the graphics system only draws primitives, and everything else is a composition of them (Lesson 2 video, W2 p.16).

Worked example

Reading gl.glDrawArrays(GL_POINTS, 0, 3) argument by argument (W2 p.5).

  1. mode = GL_POINTS. Treat each vertex as a separate point primitive.
  2. first = 0. Start at the first vertex in the array that's been handed to OpenGL.
  3. count = 3. Use three vertices. Chen's words are "from the beginning, we have three points, so we are drawing three points" (Lesson 2 video).
  4. Result is three dots. With GL_TRIANGLES † the same three vertices would make one filled triangle (the triangle mode name isn't on the Week 2 slides).

Easy to get wrong

  • "An object corresponds to a number" or "a color." Wrong. It corresponds to a model stored in the computer and an image on the screen (W2 p.3). Both of those were correct on Quiz 2.
  • "A model is stored as a framebuffer" or "as an image." Wrong. The framebuffer holds the image, which is the output. The model is vertices and colors (W2 p.3).
  • "A graphics library is a library of 2D or 3D images" or "a set of models." Wrong. It's a set of graphics commands, an API (W2 p.4, W2 p.6). The images and models are what you make with it.
  • "A 3D object is a primitive." Wrong. Primitives are point, line and triangle. A 3D object is built from them (W2 p.4, W2 p.16).
  • Chen's textbook says primitives are "points, lines, and polygons" (Chen Ch.1 p.2), but the slides and the Quiz 2 key say triangle. Go with point, line, triangle for the quizzes.

The first program and GLEventListener

The idea

JOGL1_0_Frame opens a window and fills it with cyan. That's all it draws, but it shows the skeleton every later program uses.

The program is event-driven. main() only creates the object. The constructor builds the window. Then the program just waits, and JOGL calls your methods (init, reshape, display, dispose) when things happen. You never call them yourself.

What to know

The class header is class JOGL1_0_Frame extends Frame implements GLEventListener (W2 p.7). Frame is the AWT window, and GLEventListener is the interface that brings the OpenGL callbacks (Lesson 2 video).

main() instantiates the class, which calls the constructor (W2 p.7). The object isn't even saved to a variable (Lesson 2 video).

The constructor (W2 p.8) does this, in order.

  1. Specify a drawable, the GLCanvas.
  2. Listen to the events init, reshape, display and dispose (canvas.addGLEventListener(this)), then add the canvas to the frame.
  3. Set the frame size and make it visible.
  4. Wait for the external window destroy event, disposing resources before exit.

After the constructor, the system is in the event loop (W2 p.8). Chen's distinction is that the frame is the window, and the canvas is added to it and is what you paint on (Lesson 2 video).

EventWhen (W2 p.9 and Lesson 2 video)In JOGL1_0_Frame

reshape()After init, and every time the drawing area is resized. Gets x, y, width, heightOnly prints
display()For rendering, after every reshapeClears the color buffer
dispose()To release OpenGL resources for the drawable, manually called before exitOnly prints
windowClosing()When the user closes the window. AWT event, not a GLEventListener oneCalls dispose, then System.exit(0)

The four GLEventListener methods must all be present even if empty, because the interface requires them (Lesson 2 video).

The two GL calls (Lesson 2 video).

gl = (GL4) drawable.getGL();               // init: handle to OpenGL commands
gl.glClearColor(0.0f, 1.0f, 1.0f, 1.0f);   // init: specify clear color (R,G,B,A), cyan
gl.glClear(GL_COLOR_BUFFER_BIT);           // display: actually clear every pixel to it

glClearColor only specifies the color, it doesn't draw. glClear(GL_COLOR_BUFFER_BIT) is the action that sets every bit in the color buffer to it. Alpha is ignored for now. (0,1,1) is cyan, (1,1,1) white, (0,0,0) black (Lesson 2 video).

Worked example

Tracing the console when you run the program, resize the window once, then close it.

  1. main runs new JOGL1_0_Frame(). The constructor prints Hello, JOGL! and the window appears.
  2. a) init is called once for initialization. The GL handle is fetched and the clear color is set to cyan.
  3. b) reshape is called whenever the frame is resized. It fires right after init because the window was just given its size.
  4. c) display is called for every reshape. The back buffer is cleared to cyan, then the buffers swap and the cyan shows up. Chen saw this line print twice per reshape and tied it to the two buffers (Lesson 2 video).
  5. You drag the window edge. b) prints again, then c) again. init does not repeat.
  6. You click close. windowClosing runs, calls dispose(), then System.exit(0).

Easy to get wrong

  • "GLEventListener waits for the window destroy event." Wrong. Its four events are init, reshape, display and dispose. Window destroy is the external AWT event handled by the WindowAdapter (W2 p.7, W2 p.8). This was the Quiz 2 distractor.
  • "Reshape happens after display is called." Wrong, it's the other way round. Display is called after reshape (W2 p.9).
  • "Reshape happens only once, like init." Wrong. It happens after init and again whenever the drawing area's size changes (W2 p.9, Lesson 2 video).
  • "glClearColor paints the background." Wrong. It only sets the color. glClear in display does the clearing (Lesson 2 video).
  • "setSize sets the canvas to 800 by 800." It sets the frame, which includes the title bar, so the drawable area is a bit smaller †. Mohamed measured about 800 by 772 on his Mac (his HW2 notes, not on the slides).

Framebuffers and double buffering

The idea

The framebuffer is memory with one slot per screen pixel, holding that pixel's RGB color. OpenGL writes the picture there, and a piece of hardware called the video controller reads it and sends it to the display.

There are two of them. OpenGL draws into the back buffer while the video controller reads the front buffer. When drawing's done, they swap. You never see a half-drawn picture, and the drawing side and the display side can work at the same time.

What to know

By default there are two framebuffers, the front buffer and the back buffer (W2 p.10).

OpenGL draws into the back buffer, then the buffers swap so the back becomes the front and the front becomes the back (W2 p.10).

The swap happens after display() is called, that is, after rasterization is finished. Then the front buffer image is shown (W2 p.10, Quiz 2 key).

The video controller reads the front buffer and sends it to the display (W2 p.10). The front buffer corresponds to the display, and the video controller refreshes the display with it (W2 p.15).

Why two. The hardware can't draw into a buffer and read from that same buffer at the same time, so two buffers let drawing and display overlap. One buffer would work logically, just not as well (Lesson 2 video).

You can force drawing into the front buffer, but Chen sets that aside (Lesson 2 video).

Worked example

One frame cycle, step by step.

  1. Buffer A is front, holding the old image. The video controller is reading A to the screen.
  2. display() runs. glClear and any drawing calls rasterize into buffer B, the back buffer.
  3. display() returns. The buffers swap. B is now front, A is now back.
  4. The video controller reads B and the new image appears. A is free for the next frame.

A size calculation † (not on the slides). With 800 by 800 pixels at 3 bytes of RGB each, one buffer needs \(800 \times 800 \times 3 = 1{,}920{,}000\) bytes, about 1.9 MB, and double buffering doubles that to about 3.8 MB.

Easy to get wrong

  • "OpenGL draws into the front buffer." Not by default. It draws into the back buffer, which is why Quiz 2 matched back buffer with rasterization (W2 p.10).
  • "The video controller reads the back buffer." Wrong. It reads the front buffer (W2 p.10).
  • "The swap happens before display()." Wrong. It happens after display() finishes rasterizing (W2 p.10).
  • "Framebuffers means one buffer." In this course it means the front buffer and the back buffer (W2 p.10, Quiz 2 key).

The graphics system, events, animation and history

The idea

Put it together. Your application program builds and changes models, calls OpenGL, the graphics hardware rasterizes the model into the framebuffer, and the video controller shows it. Keyboard and mouse input come back to the program as events.

Animation is just redrawing. Draw the object, clear, draw it slightly moved, repeat fast enough and the eye sees motion.

What to know

The graphics system generates the image in the framebuffer and displays it. The application program accepts user input and controls the model (create, store, retrieve, modify, send to the graphics system) (W2 p.13).

The digitization step that turns a model into an image is called scan-conversion or rasterization (W2 p.13). Chen says to just think of it as drawing. "Scan" because you go pixel by pixel, "raster" because pixels used to be called rasters (Lesson 2 video).

The diagram flow is application program and graphics models, then computer and OpenGL, then graphics hardware, framebuffer, video controller, display, with keyboard and mouse as input (W2 p.13).

The programmer's job is creating and changing the model and handling user interaction. The graphics library provides output routines for primitives and attributes (W2 p.14).

An event is a user input or other state change. Events are queued in time order and handled in that order by the system or user event handlers (W2 p.15). A timer reaching zero is also an event (Lesson 2 video).

The screen is a window for manipulating not only the image but the model behind it (W2 p.15).

Complex shapes are dissected into or built from primitives. If you can draw a pixel you can draw a point, line, triangle, curve, surface. Draw, clear, redraw at a slightly different location or orientation, repeat, and the object is animated (W2 p.16).

Worked example

Following one mouse drag that resizes the window through the system (W2 p.13, W2 p.15).

  1. The user drags the window edge. That input is an event and goes into the queue in time order.
  2. The system takes it off the queue and calls the handler, here reshape().
  3. Then display() runs and OpenGL rasterizes into the back buffer.
  4. The buffers swap, the video controller reads the front buffer, the display updates.

Easy to get wrong

  • "Cg became the standard." Wrong. Cg stopped being updated in 2013 and GLSL won (W2 p.12).
  • "OpenGL 4 still has the OpenGL 3 deprecated features." Wrong. They were marked deprecated in 3 and removed in 4 (W2 p.12).
  • "Graphics software moved toward device-dependent packages." Backwards. It moved to high-level, device-independent ones (W2 p.12).
  • "Rasterization and scan-conversion are different steps." Same thing, two names (W2 p.13).

Display devices and the framebuffer

The idea

The framebuffer is a chunk of memory with one entry per pixel on the screen. Each entry holds an RGB value, or a single intensity on a gray display. Everything a display device does comes down to reading those values and turning them into light (or toner) at the matching spot. Chen covers three devices and they all follow that same pattern with different materials.

A CRT fires an electron beam whose strength comes from the pixel value. An LCD uses a voltage to decide how much light gets through two polarizing filters. A laser printer uses a laser to write a charge pattern on a drum, and toner sticks to that pattern. Once you see that they all just read the framebuffer, the rest of the course can focus on getting the right image into the framebuffer and forget about the display side, because the hardware does that part automatically.

What to know

The objectives slide says the pixel array (image) in the framebuffer is sent to the display, which can be a CRT, LCD, printer, and so on (W3 p.2).

CRT. The intensity read from the framebuffer controls an electron gun. A magnetic yoke deflects the beam up/down and left/right so it hits the right spot. The beam hits a phosphor coating, which emits light in proportion to the beam's intensity. The beam sweeps one horizontal line, does a horizontal retrace to the next line, and after the last line does a vertical retrace back to the top. An oscillating circuit keeps the yoke synchronized with the reading. A color CRT uses three beams, one each for R, G and B (W3 p.3, Lesson 3 video).

LCD. Liquid crystal is a substance between a liquid and a solid state. An electrical charge can straighten its molecules (W3 p.4). A polarizing filter passes only one plane of light, and two filters together pass or block light depending on their relative orientation (W3 p.5). The bottom filter is called the analyzer.

ModeVoltageWhat the crystal doesResult
OfflinenoneLight polarized by the upper plate twists along the crystal and ends up parallel to the analyzerLight passes, screen looks transparent (bright)
Onlineapplied between the platesMolecules straighten, light stays perpendicular to the analyzerLight blocked, screen looks dark

That table is from (W3 p.6). Chen adds that the voltage follows the framebuffer value, and partial voltage straightens the molecules only partly, so you get dimmed light and not just on or off (Lesson 3 video).

Laser printer. The framebuffer intensity drives a laser. A deflection system (the yoke's equivalent) aims it at a rotating drum coated with selenium, which is positively charged and loses charge where the laser hits it. Negatively charged toner sticks to the charge pattern and transfers to the paper. It takes seconds per page, so you can't animate on a printer (Lesson 3 video).

Refresh rate. Most displays refresh at 60 frames per second. The reason is the human eye, which sees images swapped faster than about 30 frames per second as smooth motion. Chen calls a 120 Hz monitor for ordinary use a waste of money, because the eye can't tell 60 from 120. Displays that really run at 120 do it to send 60 frames per second to each eye (stereo/VR). The framebuffer can have left front, left back, right front and right back buffers for stereo, but this course only uses one front and one back buffer (Lesson 3 video).

Worked example

Follow one pixel whose framebuffer value is dark gray on each device.

  1. CRT. The video controller reads the value and the gun fires a weak beam. The yoke aims it at that pixel's spot, and the phosphor glows faintly.
  2. LCD. The value sets a fairly high voltage across that pixel's crystal, so most molecules straighten. Most of the light stays perpendicular to the analyzer and gets blocked, so the pixel looks dark gray, not fully black.
  3. Printer. The laser hits the drum at that spot with a matching intensity, the selenium charge changes by that amount, and the toner amount follows.
  4. In every case the device only read the framebuffer. That's why the rest of the course is about writing the right values into it (Lesson 3 video).

Easy to get wrong

  • "Applying voltage to an LCD pixel makes it bright." Wrong. Voltage is the online mode, which straightens the crystal and blocks the light, so it goes dark. With no voltage (offline) the light twists through and passes (W3 p.6).
  • "Refresh rates keep improving the picture, so 120 Hz beats 60 Hz for a normal display." Chen says the eye can't tell the difference past 60, and 120 Hz displays exist to feed two eyes 60 each (Lesson 3 video).
  • "The two filters in an LCD are the polarizer and the liquid crystal." The two filters are the top polarizer and the bottom analyzer. The crystal sits between them and twists the light (W3 p.5 to 6).

Raster display system, graphics card and GPU

The idea

Picture the computer as a CPU and memory on a bus, with a graphics card plugged into that bus. The card has three parts. The GPU does the graphics work and produces the image. The framebuffer holds that image. The video controller keeps reading the framebuffer and refreshing the display. The display itself and the computer's CPU are not part of the card.

The GPU is called the graphics card's CPU, but it works differently from a normal CPU. It's many processing units running the same program at the same time on different data. That's exactly what shaders need, one small program run once per vertex or once per pixel, all at once.

  • "The video controller does the scan-conversion." No, the graphics card does scan-conversion. The video controller only reads the framebuffer and refreshes the display (W3 p.7).

The rendering pipeline order

The idea

The pipeline is the path from "here are some vertices" to "these pixels are colored in the framebuffer." The CPU specifies the vertices. The vertex shader runs on each vertex separately. But a vertex alone isn't a shape, so the vertices then get put back together into their primitive (a point, line or triangle). Only once you have the whole primitive can you clip it against the boundary, since clipping cuts a shape and you can't cut a shape you haven't built yet. The clipped primitive is rasterized, which finds every pixel inside it. Finally the fragment shader runs once per pixel to pick its color, and the result goes into the framebuffer.

The graded order is Vertex Specification, Vertex Shader, Primitive Assembly, Clipping, Rasterization, Fragment Shader. A way to remember it is "Very Vain People Can't Resist Fame." The key link is that assembly makes the triangle and clipping cuts the triangle, so assembly has to come first.

Worked example

Trace one triangle with one corner sticking out past the right edge (x = 1.4).

  1. Vertex Specification. The CPU sends an array of 3 vertices and says they form a triangle.
  2. Vertex Shader. Three copies of the same program run in parallel, one per vertex. Each copy only sees its own vertex. No copy knows it's part of a triangle (Lesson 3 video).
  3. Primitive Assembly. The three processed vertices are put back together as a triangle. Now there are edges.
  4. Clipping. The triangle is cut at x = 1. The edges that cross the boundary get new points where they meet x = 1, so the shape becomes a four-sided piece inside the view. This step needed the edges from step 3, which is why it can't come first.
  5. Rasterization. Find every pixel inside the clipped shape.
  6. Fragment Shader. One copy runs per pixel found in step 5, all in parallel, and outputs a color. The colors are written into the framebuffer.

Easy to get wrong

  • Swapping Primitive Assembly and Clipping. This cost him points on quiz 3 Q3 attempt 1. Clipping cuts a whole primitive against a boundary, so the primitive must be assembled first (W3 p.19).
  • Putting Rasterization before Clipping. You'd be finding pixels for parts of the shape that will be thrown away. Clip first, then rasterize (W3 p.19).
  • Putting the fragment shader right after the vertex shader. The fixed steps in between (assembly, clipping, rasterization) are what produce the pixels the fragment shader runs on (W3 p.19, Lesson 3 video).
  • "Tessellation and geometry processing are required steps." Slide 10 marks both optional, and Chen skips them until late in the course (W3 p.10, Lesson 3 video).

Parallelism, per-vertex values and uniform values

The idea

You write one vertex shader, but the GPU runs a copy of it for every vertex at the same time. A triangle gives 3 copies, and 10 triangles give 30. The copies are identical programs, so the only thing that makes them do different work is the data each one gets, like its own vertex position (Lesson 3 video). The fragment shader works the same way, with one copy per pixel.

That splits the data into two kinds. A per-vertex value can be different at each vertex, like the vertex position. A uniform value is the same for every vertex of the primitive, like the viewpoint, a light source position, or the color of a triangle that's all one color. The quiz questions on this are about sorting values into those two buckets.

What to know

Only the vertex shader and fragment shader are parallel programs. "Vertex shader: parallel vertex processing. Fragment shader: parallel fragment processing" (W3 p.20, W3 p.13). Primitive assembly and rasterization are not parallel programs in Chen's model (quiz 3 Q1).

ValuePer-vertex or uniformWhy
Vertex positions of a trianglePer-vertexEach corner is at a different place
Color of a one-color (e.g. green) triangleUniformEvery vertex has the same color
Light source positionUniformOne light, same for all vertices
Viewpoint (view position)UniformOne eye position for the whole scene

That table follows the quiz 3 key (Q4 and Q6). Quiz 5 Q2 states the rule directly. Uniform values are the same for all vertices, but per-vertex values differ by vertex and are sent to the vertex shader to be processed in parallel. They are not interchangeable.

"Fragment" is the name for a pixel in the pipeline. Chen says a fragment carries more than a final color (RGB, transparency and other components), so it's a broader word than pixel. Calling it a pixel shader is fine too (Lesson 3 video).

Worked example

A green triangle lit by one lamp, viewed from one camera. Sort its data.

  1. Ask for each value, "could it differ between corner A and corner B?"
  2. Positions. Yes, otherwise it isn't a triangle. Per-vertex.
  3. Color. No, the whole triangle is green. Uniform.
  4. Lamp position. No, there's one lamp. Uniform.
  5. Camera position. No, there's one viewer. Uniform.
  6. So the vertex shader runs 3 copies, each getting a different position but the same color, light and viewpoint.

Easy to get wrong

  • "Primitive assembly and rasterization are parallel programs." Only the vertex shader and fragment shader are (W3 p.20, quiz 3 Q1).
  • "The color of a uniform-color primitive differs among vertices." By definition it's the same at every vertex, so it's uniform, not per-vertex (quiz 3 Q4).
  • "Light source position and viewpoint are per-vertex." There's one of each for all the vertices, so they're uniform (quiz 3 Q4, Q6).
  • "Vertex positions of a triangle are uniform." They're the textbook per-vertex value, since the corners are in different places (quiz 3 Q6).
  • "Uniform and per-vertex values are the same thing, you can send either way." Quiz 5 Q2 marks every "no difference" option wrong.

JOGL1_0_Point, shaders inside the program

The idea

JOGL1_0_Point is Week 2's frame program plus one red point. It extends JOGL1_0_Frame, so it gets the window, canvas and event handlers for free and only replaces init() and display(). In init() it writes a vertex shader and a fragment shader as Java string arrays and hands them to initShaders(), which compiles them and loads them onto the GPU. In display() it asks OpenGL to draw one point, which triggers the vertex shader and then the fragment shader.

The vertex shader hard-codes the position (0, 0, 0), the center of the window. The fragment shader hard-codes red. Since there's only one vertex, the "parallel" vertex shader runs just one copy here.

What to know

Event order. init() is called once to initialize the shader programs. reshape() is called once, and then after every reshape of the drawing area. display() is called once and again (for front and back buffers). Then the vertex shader runs per vertex and the fragment shader per pixel (W3 p.13). Quiz 3 Q2 adds primitive assembly between the two shaders.

Inheritance. The subclass inherits the superclass's methods, hidden from view. Creating the object calls the super's constructor first, which does the frame initialization. You replace methods like init() and display() by writing new ones. In Eclipse, F4 or right-click "Open Type Hierarchy", then "Show all inherited members" shows everything available (W3 p.14). A replaced method can still be called with super. (Lesson 3 video).

main() creates the object, sets the title, size (WIDTH*3/2, HEIGHT) and location (20, 20 for the frame's upper-left corner), then the program waits in the event loop (W3 p.15).

Worked example

What happens from main() to the red dot.

  1. new JOGL1_0_Point() calls JOGL1_0_Frame's constructor first. It makes the canvas, adds the event listener, sets the size and shows the window (W3 p.14).
  2. Back in main(), title, size and location are set. The program enters the event loop (W3 p.15).
  3. init() runs once. It gets the GL4 handle, builds the two shader strings, and initShaders() compiles, attaches, links and uses them (W3 p.17).

  • "You must declare gl_Position with out vec4." It's predefined. Only the fragment shader's color output is declared by you (W3 p.16).
  • "glLinkProgram loads the program onto the GPU." Step 5, glUseProgram, does that (W3 p.17).
  • "Link comes before attach." Attach is step 3, link is step 4. You can't link shaders that aren't in the program yet (W3 p.17).
  • "Setting glClearColor is enough to get a background." JOGL1_0_Point's display() replaces the frame's display(), which had the glClear. Without calling glClear again the color is never applied, and Chen's run shows the default black (Lesson 3 video).
  • "Things you set once go in display()." Chen's rule is the opposite. Set-once things like the clear color go in init(). Things that change go in display() or reshape(), because those are called again and again (Lesson 3 video).
  • "(0, 0, 0) is the window's top-left corner." It's the center, because the range is -1 to +1 on each axis (W3 p.16, Lesson 3 video).

public String[] readShaderSource(String filename) {

OpenGL and the libraries around it

The idea

OpenGL was written for C programmers. We write Java, so something has to sit in between and turn a Java call like gl.glDrawArrays(...) into a call on the native C library. That's JOGL. It's just OpenGL with Java bindings, so you get the full OpenGL function set and it plugs into AWT and Swing windows.

Around OpenGL there are a few helper libraries with confusingly similar names. GLU is a set of higher-level drawing routines built out of OpenGL commands. GLUT is a toolkit that made C programs portable across operating systems. GLSL is the shading language you write the GPU programs in. The quiz asks you to match these, so learn one defining phrase for each.

What to know

JNIJava Native Interface. Lets Java call C functions.(W4 p.4)

Worked example

What happens when your Java code calls gl.glDrawArrays(GL_POINTS, 0, 1)?

  1. The call lands on a Java method in JOGL's GL4 object (W4 p.3).
  2. That Java method was generated by GlueGen, along with a JNI stub (W4 p.4).
  3. JNI crosses from the Java VM into native code and calls the real C function glDrawArrays in the OpenGL driver (W4 p.4).
  4. The driver sends the vertex to the GPU, where your GLSL vertex and fragment shaders run (W4 p.7).

GLU and GLUT never enter this path. They're optional helpers sitting next to OpenGL.

Easy to get wrong

  • "GLUT provides higher-level drawing routines implemented in OpenGL." That's GLU. GLUT is the cross-platform toolkit (W4 p.6). The quiz key matches GLUT to "a toolkit to make OpenGL programs run on different platforms" and GLU to "a set of functions implemented in OpenGL to provide higher-level drawing routines".
  • "GLSL is a separate add-on library you link in." It used to be. OpenGL 4.x includes GLSL as a standard (W4 p.7).
  • "JOGL is a new graphics API." It's OpenGL bound in Java, the same functions (W4 p.3).
  • "JNI generates the Java code." GlueGen generates the Java and JNI code. JNI is the mechanism that allows the C calls (W4 p.4).

The animation loop and FPSAnimator

The idea

Animation is just drawing a slightly different picture many times a second. Movies did it with 24 still frames per second. In a JOGL program each picture is one call to display(), so to animate you need something that keeps calling display() and you need the drawing to change a little each call.

JOGL's FPSAnimator does the first part. When you start it, it starts a thread that calls display() over and over at a target rate. Your code does the second part by keeping a variable (like pos) that changes a bit each call.

What to know

Frame rates (W4 p.8). Movies project 24 frames per second. 60 f/s is smoother than 30. 120 is marginally better than 60. Faster than 120 makes no difference. Chen says most monitors are 60 f/s and some can be set to 75 (Lesson 4 video).

The Animator starts a thread that calls display() repetitively in a loop (W4 p.9). The code (W4 p.10)

FPSAnimator animator; // for thread that calls display() repetitively
animator = new FPSAnimator(canvas, 40); // 40 calls per second
animator.start();
...
// in dispose()
animator.stop(); // stop the animator thread

The 40 is a cap, not a guarantee. It calls display() at most 40 times a second. If your display() takes longer, it runs slower, but it never runs faster (Lesson 4 video). Chen fixes the rate so the animation doesn't run too fast. A plain Animator without the FPS limit can run very fast (Lesson 4 video).

The animator is created and started in the constructor, after the super constructors have opened the window. It's stopped in dispose() so the thread releases its resources before the program quits, and then super.dispose() is called (Lesson 4 video, W4 p.10).

Worked example

How long does Chen's point take to cross the diagonal once?

  1. At 40 frames per second, each display() call is \(1000/40 = 25\) ms apart.
  2. In his code pos moves by 0.01 per call once it bounces, and travels from \(-1\) to \(1\), a distance of 2. So one crossing is \(2/0.01 = 200\) frames.
  3. \(200 \times 25\text{ ms} = 5\) s. The slide version uses 0.005 (W4 p.11), which doubles it to 400 frames, 10 s.
  4. If display() got slow and the real rate dropped to 20 f/s, the crossing would take 10 s. The animator can't speed up to compensate, because 40 is a ceiling.

Easy to get wrong

  • "FPSAnimator(canvas, 40) guarantees exactly 40 frames per second." It's the most it will do. A slow display() makes it slower (Lesson 4 video).
  • "Going from 120 to 240 f/s makes animation visibly smoother." Faster than 120 makes no difference (W4 p.8).
  • "The animator calls init() repeatedly." It calls display() repeatedly (W4 p.9).
  • "You can skip animator.stop()." Chen stops it in dispose() so the thread is released before quitting (W4 p.10).

Uniform variables and parallel shaders

The idea

The animation variable lives in Java on the CPU. The shader that places the point lives on the GPU. A uniform is how you hand a value across. You look up the shader variable by its name, get back an integer location, and then write your Java value to that location.

It's called uniform because every copy of the shader gets the same value. Shaders run in parallel, one vertex shader per vertex. A light position or a viewpoint is the same for every vertex, so it's a uniform. Later in the course you'll send per-vertex values, where each copy gets its own (Lesson 4 video).

What to know

Uniform functions send a variable value from the JOGL program to the shaders. The value is uniform for all shader programs run in parallel (W4 p.9). The JOGL side (W4 p.11)

pos += delta;
if (pos <= -1.0f) delta = 0.005f;
else if (pos >= 1.0f) delta = -0.005f;
// connect a JOGL variable with a shader variable by name
int posLoc = gl.glGetUniformLocation(vfPrograms, "sPos");
gl.glProgramUniform1f(vfPrograms, posLoc, pos);

The shader side (W4 p.12)

#version 430
uniform float sPos; // value from JOGL main program
void main(void){
  // logical coordinates: -1 to 1 along x, y, and z in homogeneous coordinates
  gl_Position = vec4(sPos, sPos, 0.0, 1.0);
}

Facts Chen stresses.

  • You can create multiple uniform variables (W4 p.11). In the video he adds a second one, pos1, to move y differently from x (Lesson 4 video).
  • A uniform can go to the vertex shader, the fragment shader, or both. He demos uncommenting uniform float sPos in the fragment shader and using sPos*sPos as a color, squared so it stays in 0 to 1 (Lesson 4 video).
  • Shaders use float, not double (Lesson 4 video). † GLSL 4.0 and later does have a double type, but the course code always uses float.
  • Chen names the Java variable pos and the shader variable sPos and says they should be different names (Lesson 4 video). † The link is made by the string passed to glGetUniformLocation, so the different name is his convention. The string must match the shader's name exactly.
  • Because display() runs repeatedly, the shaders run repeatedly, each time with the new uniform value. That's what makes the point move (Lesson 4 video).

Worked example

Trace one frame where pos was 0.29 and delta is 0.01.

  1. pos += delta gives 0.30. It's between \(-1\) and \(1\), so delta stays 0.01.
  2. glGetUniformLocation(vfPrograms, "sPos") returns the integer slot for sPos in the linked program.
  3. glProgramUniform1f(vfPrograms, posLoc, 0.30f) writes 0.30 into that slot. The 1f means one float.
  4. glDrawArrays(GL_POINTS, 0, 1) runs the vertex shader once. It reads sPos = 0.30 and sets gl_Position = (0.30, 0.30, 0.0, 1.0).
  5. Next frame it's 0.31, then 0.32, so the point slides up the diagonal. When pos reaches 1.0 the delta flips to \(-0.01\) and it slides back.

If you drew a triangle instead, all three vertex shader copies would read the same 0.30. That's the uniform part.

Easy to get wrong

  • "A vertex shader is a CPU program that runs on the GPU." It's a parallel program that runs on the GPU (W4 p.7, W4 p.9). Both quiz distractors started with "a CPU program", which is how you spot them.
  • "All vertices run one vertex program serially with different input." Each vertex has its own vertex shader running in parallel (W4 p.9). Per the quiz key, the values it gets may be the same (uniform) or unique per vertex. Both of those options were correct.
  • "A uniform can only go to the vertex shader." Chen sends it to the fragment shader too (Lesson 4 video).
  • "You can only send one uniform." You can create multiple (W4 p.11).
  • The slide uses delta = 0.005f (W4 p.11) but the shipped JOGL1_2_Animate.java starts at 0.1 and bounces with 0.01. Chen says in the video he changed it. Don't be thrown if a question quotes either number.

Double buffering in animation

The idea

There are two color buffers. The front buffer is what the screen shows. The back buffer is where you draw. When a frame is done they swap, so you never see a half-drawn picture. JOGL does the swap for you after display() returns.

This matters the moment you stop clearing. Each frame draws one point into whichever buffer is the back buffer at the time. Odd frames land in one buffer and even frames in the other. Each buffer ends up holding every other point, and as they swap you see the two slightly different trails flicker. That's the "shimmering line".

What to know

  • The front buffer is displayed while the back buffer is used for scan-conversion (drawing). When a frame is complete the buffers are swapped (W4 p.8). Chen says the swap happens automatically when display() finishes, and you can also swap manually (Lesson 4 video).
  • Comment out clearing the background and you get a shimmering line, alternating points in two buffers (W4 p.13).
  • To treat the double buffer as a single buffer, call glDrawBuffer(GL_FRONT) with a glFlush(). Switch back with glDrawBuffer(GL_BACK) (W4 p.13).
  • Or draw into both at once with glDrawBuffer(GL_FRONT_AND_BACK). That may not work on all platforms, so the fallback is draw once, swap, draw again (W4 p.13).
  • Chen's code has //gl.glDrawBuffer(GL.GL_FRONT_AND_BACK); //if you want a still image commented out, and he clears every frame with glClearBufferfv(GL_COLOR, 0, bgColorBuffer), which he calls another way to set the background color (Lesson 4 video).

Worked example

Clearing is off and the point is at positions \(p_1, p_2, p_3, p_4\) in four frames. Call the buffers A and B, with B as the back buffer first.

  1. Frame 1 draws \(p_1\) into B. Swap. Screen shows B = {\(p_1\)}.
  2. Frame 2 draws \(p_2\) into A. Swap. Screen shows A = {\(p_2\)}.
  3. Frame 3 draws \(p_3\) into B. Screen shows B = {\(p_1, p_3\)}.
  4. Frame 4 draws \(p_4\) into A. Screen shows A = {\(p_2, p_4\)}.
  5. The two buffers never hold the same set, so the trail jumps between two dotted versions. With GL_FRONT_AND_BACK every point goes into both, A = B = {\(p_1,\dots,p_4\)}, and you get one steady trail.

Easy to get wrong

  • "The screen shows the back buffer." It shows the front buffer. You draw into the back (W4 p.8).
  • "Not clearing gives a solid, still trail." It gives a shimmering line because the two buffers hold different points (W4 p.13).
  • "glDrawBuffer(GL_FRONT) alone is enough." The slide pairs it with glFlush() (W4 p.13).
  • "GL_FRONT_AND_BACK works everywhere." The slide says it may not work on all platforms (W4 p.13).

Window vs viewport, gl_Position vs gl_FragCoord

The idea

The window is the physical area on screen, measured in pixels. The viewport is a rectangle inside it where drawing actually goes. By default the viewport is the whole window, which is why you didn't notice the difference before.

The two shaders see two different coordinate systems. The vertex shader writes gl_Position in logical coordinates, \(-1\) to \(1\) across the viewport no matter how many pixels it has. The fragment shader reads gl_FragCoord, which is the pixel's real location in the window. Vertex shader is logical, fragment shader is physical.

glViewport(int x, int y, int width, int height). The first two are the lower-left pixel, the last two the width and height, all in pixels in the window (W4 p.14).

gl.glDrawArrays(GL_POINTS, 0, 1);
// This is the upper-right quad
gl.glViewport(400, 400, 400, 400);
gl.glDrawArrays(GL_POINTS, 0, 1);

Vectors, dot product, cross product, reflection

The idea

A vector has a length and a direction, but no position. Graphics mostly cares about two questions. What's the angle between two directions, and what direction is perpendicular to a surface? The dot product answers the first, the cross product the second. Both come back later for lighting, where you need the cosine between the light and the normal (Lesson 4 video).

A quick way to keep them apart. Dot gives a number (a scalar). Cross gives a vector.

Chen's normalize checks for a zero-length vector and returns with an error (W4 p.17). GLSL's built-in doesn't check, so you must make sure the vector isn't zero before calling it (Lesson 4 video).

Reflection reasoning (W4 p.20). \(\mathbf v_1\cdot\mathbf n\) is the length of \(\mathbf v_1\)'s projection on \(\mathbf n\). Twice that, times \(\mathbf n\), is a vector along \(\mathbf n\). Subtract \(\mathbf v_1\) and you get \(\mathbf v_2\). In Chen's picture both \(\mathbf v_1\) and \(\mathbf v_2\) point away from the surface. He says reflect is used later for ray tracing (Lesson 4 video).

† Not on the slides. GLSL's real reflect(I, N) computes \(I - 2(N\cdot I)N\), with \(I\) pointing toward the surface. For the same \(\mathbf v_1\) that's the negative of Chen's \(\mathbf v_2\). Also † \(\mathbf a\times\mathbf b = -(\mathbf b\times\mathbf a)\), so order matters.

Worked example

Angle between \(\mathbf a = (1,2,2)\) and \(\mathbf b = (3,0,4)\).

  1. \(\mathbf a\cdot\mathbf b = 1\cdot3 + 2\cdot0 + 2\cdot4 = 11\).
  2. \(|\mathbf a| = \sqrt{1+4+4} = 3\), \(|\mathbf b| = \sqrt{9+0+16} = 5\).
  3. \(\cos\theta = 11/15 \approx 0.7333\), so \(\theta \approx 42.83^\circ\).

Cross product of \(\mathbf a = (1,2,3)\) and \(\mathbf b = (4,5,6)\).

  1. \(x = a_1b_2 - a_2b_1 = 2\cdot6 - 3\cdot5 = -3\).
  2. \(y = a_2b_0 - a_0b_2 = 3\cdot4 - 1\cdot6 = 6\).
  3. \(z = a_0b_1 - a_1b_0 = 1\cdot5 - 2\cdot4 = -3\).
  4. Check. \((-3,6,-3)\cdot(1,2,3) = -3+12-9 = 0\) and \((-3,6,-3)\cdot(4,5,6) = -12+30-18 = 0\). Perpendicular to both.

Normalize \((3,4,0)\). Length 5, so the unit vector is \((0.6, 0.8, 0)\).

Reflect \(\mathbf v_1 = (1,1,0)\) about \(\mathbf n = (0,1,0)\). \(\mathbf v_1\cdot\mathbf n = 1\), so \(\mathbf v_2 = 2\cdot1\cdot(0,1,0) - (1,1,0) = (-1,1,0)\). Same height, mirrored across the normal, like a bouncing ball.

  • "Use the cross product to find the angle between two vectors." Use the dot product. It gives \(\cos\theta\) directly (W4 p.18). Quiz 4 Q4.
  • "Use the dot product to find a vector perpendicular to two vectors." Use the cross product (W4 p.19). Quiz 4 Q5.
  • "Multiplication" or "addition" of the vectors were distractors on both questions. Neither gives an angle or a perpendicular (W4 p.18 to 19).
  • "The dot product returns a vector." It returns a scalar. The cross product returns a vector (W4 p.18 to 19).
  • "Normalizing changes the direction." It keeps the direction and makes the length 1 (W4 p.17).
  • "The reflection formula works with any \(\mathbf n\)." \(\mathbf n\) must be normalized (W4 p.20).

Matrices, lines, planes, circles and spheres

The idea

This is the math toolbox for later weeks. Matrices will move objects around (transformations). Line, plane and circle equations are how you compute points to draw. The circle one matters right now because the homework animates a point on a circle.

What to know

  • Identity matrix. Ones on the diagonal. Multiplying by it changes nothing, like multiplying a number by one (W4 p.22). Chen says it's how you initialize before building transformations (Lesson 4 video).
  • Addition is componentwise. Multiplication is row times column. In GLSL + and * are overloaded on mat4 (W4 p.23).
  • Transform a vertex by multiplying a 4x4 matrix by \((X, Y, Z, 1)\). GLSL overloads * for this (W4 p.24). The 1 is the homogeneous coordinate, covered later (Lesson 4 video).
  • Inverse \(M^{-1}\) with \(M^{-1}M = MM^{-1} = I\). Transpose \(M^T\) flips across the diagonal, GLSL transpose(mat4) (W4 p.25). The slide writes the inverse as mat4.inverse(). † Real GLSL spells it inverse(m). Chen says if vertices are transformed by \(M\), normals are transformed by the inverse transpose of \(M\) (Lesson 4 video).

  • Step angle for a circle. Circumference is \(2\pi r\) pixels, so to move one pixel per step use \(\Delta\theta = 2\pi/(2\pi r) = 1/r\) (W4 p.29, Lesson 4 video).

Worked example

Plane through \(P=(1,0,0)\), \(Q=(0,1,0)\), \(R=(0,0,1)\).

  1. Two vectors in the plane. \(Q-P = (-1,1,0)\), \(R-P = (-1,0,1)\).
  2. Cross. \((1\cdot1-0\cdot0,\; 0\cdot(-1)-(-1)\cdot1,\; (-1)\cdot0-1\cdot(-1)) = (1,1,1)\). That's \((a,b,c)\).

Line point. \(P=(1,2,3)\), \(Q=(5,6,7)\), \(t=0.25\) gives \(0.75P + 0.25Q = (2,3,4)\).

Circle steps. A circle of radius 200 pixels needs \(\Delta\theta = 1/200 = 0.005\) rad and \(2\pi\cdot200 \approx 1256.6\) steps. At 40 f/s that's about 31.4 s per lap.

Where rasterization sits in the pipeline

The idea

Your JOGL program packs per-vertex data into arrays and ships them to the GPU. The vertex shader runs one copy per vertex, all at once. After that the system glues the vertices back into points, lines, or triangles, cuts off whatever falls outside the window, and then works out every pixel the shape covers. Each of those pixels gets its own fragment shader run, again in parallel, and the result lands in the framebuffer.

So the work alternates. Parallel on the GPU for vertices, then a fixed set of system steps (assembly, clipping, scan-conversion), then parallel on the GPU for pixels. This lesson is about those middle steps, which Chen treats as the "CPU side" of the pipeline.

What to know

The lesson's objectives are VAO/VBO for per-vertex values, rasterization algorithms, clipping, and the efficiency of these functions, where "execution time efficiency is the key" (W5 p.2). Reading is Chen 1.3 and Gordon 4.1, 4.2 (W5 p.2).

VAO, VBO, per-vertex values and uniforms

The idea

A uniform is one value that every shader copy sees the same, like a single number broadcast to everyone. A per-vertex value is different for each vertex, like each corner's own position. You can't send a list of different positions as a uniform, so you put them in an array, wrap the array in a buffer, and upload it to graphics card memory. That buffer is a VBO.

A VAO is the container that bundles several VBOs together for the vertex shader. In the shader, each VBO shows up at a numbered layout (location = n), and each parallel shader copy pulls its own slice from it.

The win is speed. The data sits in GPU memory and every vertex is processed at the same time, instead of one point per draw call.

What to know

VBO means arrays that store vertex positions (vPosition), colors (vColor) and other per-vertex information for a primitive. VAO means the array(s) that pack multiple VBO arrays for transfer to the vertex shader (W5 p.5). Per-vertex values include position, color, normal and texture coordinates, and the shader retrieves them in parallel (W5 p.4).

The five-step procedure (W5 p.5 to 7). Steps 1, 2 and 5 happen once in init(). Steps 3 and 4 can be redone in display() when the data changes, which is how you animate (W5 p.7 to 8, Lesson 5 video).

Scan-converting lines with the basic incremental algorithm

The idea

The screen is a grid. A line from one integer pixel to another passes between pixel centers, so you have to pick which pixels to light. The simplest way steps x by one pixel at a time and adds the slope to y each step. Since y is a fraction, you round it to the nearest row.

It works but it uses floating-point adds and a rounding every step. That's why Bresenham's integer-only version comes next.

What to know

Slope \(m = \Delta y / \Delta x\). The line is \(y_i = m x_i + B\), so \(y_{i+1} = y_i + m\). Intensify the pixel at \((x_i, \text{Round}(y_i))\) (W5 p.16). The slides call this the basic incremental algorithm. Many books call it DDA † (that name isn't on the slides).

void line(int x0,int y0,int xn,int yn) { // for -1 <= m <= 1
  int x; float m, y;
  m = (float) (yn-y0)/(xn-x0);
  x=x0; y=y0;
  while (x<xn+1) {
    // write a pixel into the framebuffer
    x++; y+=m; /* next pixel's position */
  }
}

It only works for \(-1 \le m \le 1\), where x is the faster-changing axis (W5 p.16). In Chen's simulation the pixels go into an array, nPixels = xn - x0 + 1, each normalized to the -1 to 1 range, then the whole array is uploaded once and drawn with glDrawArrays(GL_POINTS, 0, vBuf.limit()/3) (W5 p.19 to 20). JOGL_1_4_2_Line draws a yellow line with OpenGL's own GL_LINES and a green line with this algorithm (W5 p.17 to 18). Chen notes the extra math maps the 0 to WIDTH and 0 to HEIGHT pixel grid into -1 to 1 (Lesson 5 video).

Bresenham's midpoint line algorithm

The idea

Assume a slope between 0 and 1. From the current pixel the next one is either straight right (E) or up and to the right (NE). Look at the midpoint between those two candidates. If the true line passes above that midpoint, go NE. Otherwise go E.

You test "above or below" by plugging the midpoint into the line equation \(F(x,y)\) and checking the sign. The trick is that each new test value is just the old one plus a constant, and after multiplying everything by 2 those constants are integers. So each step is one comparison and one integer add, which is cheap and easy to build in hardware.

What to know

Chen's notation (W5 p.21 to 22, Chen book 1.3). The line is \(F(x,y) = ax + by + c = 0\) with \(a = dy = y_n - y_0\), \(b = -dx = -(x_n - x_0)\), and \(c = B\,dx\). Current pixel is \(P(x_p, y_p)\), midpoint is \(M = (x_p+1,\ y_p+\tfrac12)\), and Q is where the line crosses between E and NE.

If \(F(M) > 0\), Q is above M (the line is above the midpoint), so choose NE. Otherwise choose E (W5 p.22).

\[d_{old} = F(x_p+1,\ y_p+\tfrac12) = F(x_p,y_p) + a + \tfrac{b}{2} = a + \tfrac{b}{2}\]

If E is chosen, the next midpoint is \((x_p+2,\ y_p+\tfrac12)\) and \(d_{new} = d_{old} + a\). If NE is chosen, the next midpoint is \((x_p+2,\ y_p+\tfrac32)\) and \(d_{new} = d_{old} + a + b\) (W5 p.22).

Only the \(b/2\) is a fraction, so multiply by 2. Doubling doesn't change the sign, so the decisions stay the same (W5 p.22, Lesson 5 video).

That's from (W5 p.23), example JOGL1_4_3_Line. The core case is \(0 \le m \le 1\). In the book's code, it swaps endpoints if \(x_n < x_0\), negates y if \(y_n < y_0\) (flag 10), and swaps x and y if \(dx < dy\) (flag+1), so flag is 0, 1, 10 or 11.

Chen says it's also called the midpoint line algorithm, it's an integer algorithm, and that makes it more efficient and easier to put in hardware (Lesson 5 video). He dates it to Jack Bresenham in 1962 in the video, while his book cites Bresenham's 1965 IBM Systems Journal paper.

Scan-converting circles and other curves

The idea

A circle is symmetric eight ways. Compute one eighth (a 45 degree arc) and mirror each point into the other seven octants by swapping and negating x and y.

Solving \(y = \sqrt{R^2 - x^2}\) is slow and spaces the pixels unevenly, because y changes fast near the sides. Stepping the angle in polar form fixes the spacing. If you want pixels about one unit apart, there are \(2\pi r\) of them around the circle, so the angle step is \(2\pi / 2\pi r = 1/r\).

What to know

Eight-way symmetry. One computed point \((x,y)\) gives \((x,y), (y,x), (y,-x), (x,-y), (-x,-y), (-y,-x), (-y,x), (-x,y)\) (W5 p.24). The square-root method is time consuming and the space between pixels isn't uniform (W5 p.24). The slide text says x goes "from 0 to R/2". The 45 degree point is actually at \(x = R/\sqrt2\) †, so read that as the end of the first octant.

Polar form \(x = x_c + r\cos\alpha\), \(y = y_c + r\sin\alpha\), with delta = 1/r and the loop while (th <= Math.PI/4) drawing 8 mirrored points per step (W5 p.25). Chen explains the \(1/r\) step comes from \(2\pi / (2\pi r)\), and too small a step makes pixels pile up while too big makes a dotted circle (Lesson 5 video). The slide spells it "Poloar", and Chen noticed the typo on camera (Lesson 5 video).

Conics \(Ax^2 + By^2 + Cxy + Dx + Ey + F = 0\). The slide classifies with \(B^2 - 4AC\). Less than 0 is an ellipse or circle, 0 is a parabola, greater than 0 is a hyperbola (W5 p.26). † In the usual form the xy coefficient is B (\(Ax^2 + Bxy + Cy^2\)), which is what makes \(B^2 - 4AC\) work. The slide's letters are shuffled, so if a question writes the equation out, use the xy coefficient squared minus 4 times the product of the \(x^2\) and \(y^2\) coefficients.

Parabolic path \(x = x_0 + v_{x0}t\), \(y = y_0 + v_{y0}t - gt^2/2\). Hyperbolic path \((x/r_x)^2 - (y/r_y)^2 = 1\) (W5 p.26).

Cubic curves \(x = a_x + b_x t + c_x t^2 + d_x t^3\) (same for y, z), \(0 \le t \le 1\). A 3D spline joins sections so adjacent ones share the boundary position and have equal slopes there. Polynomials are useful for object shapes, animation paths and graphing data trends (W5 p.27). Chen adds that the cubic is the lowest degree curve that wiggles in 3D and the course won't cover curves much (Lesson 5 video).

Worked example

Circle of radius r = 200 pixels.

  1. Points for one-pixel spacing are \(2\pi r = 2\pi(200) \approx 1257\).
  2. Angle step is \(1/r = 1/200 = 0.005\) radians.
  3. The loop only runs th from 0 to \(\pi/4 \approx 0.785\), about \(0.785/0.005 \approx 157\) steps, and each step writes 8 points, so roughly \(8 \times 157 \approx 1257\) points total.

Easy to get wrong

  • "Using \(y = \sqrt{R^2-x^2}\) with x stepping by 1 gives evenly spaced pixels." No. Spacing isn't uniform and it's slow (W5 p.24).
  • "The angle step for one-pixel spacing is \(2\pi r\)." That's the number of points. The step is \(1/r\) (W5 p.25).
  • "You need to compute the full 360 degrees." Only 0 to \(\pi/4\), then mirror 8 ways (W5 p.25).

Filling polygons with the Edge Table and Active Edge Table

The idea

Sweep a horizontal scan-line from the bottom of the polygon to the top. On each scan-line find where it crosses the polygon's edges, sort those crossings left to right, and fill between pairs. The first crossing is where you enter the polygon, the second is where you leave, and so on.

Doing that from scratch on every row would be slow, so the algorithm takes two passes. First build an Edge Table (ET) that files every edge under its lowest y. Then sweep up and keep an Active Edge Table (AET) of just the edges the current scan-line crosses. Each active edge stores its current x, and moving up one row means adding \(1/m\) to that x, the same incremental trick as the line algorithms.

What to know

Rectangles are trivial, a double loop over y and x writing every pixel (W5 p.28). A polygon is given as a list of vertices. Build a list of edges (the ET), where given y the x comes from the edge's line equation. Fill each scan-line inside the polygon by finding the intersections with all edges, sorting them by increasing x, and filling pixels between pairs of intersections that lie interior to the polygon (W5 p.28).

ET has all edges sorted by the smaller y coordinate. AET corresponds to the current scan-line (W5 p.29). Each ET entry, as Chen reads it off the figure, holds \(y_{max}\), the x at the lower endpoint, and \(1/m\). It's stored in the bucket for its lower y. \(1/m\) is stored because adding it to x gives the next row's x, and \(y_{max}\) is stored so you know when the edge is finished (Lesson 5 video).

The algorithm, in the slide's order (W5 p.30).

  1. Build an ET from the list of vertices.
  2. Set y to the smallest y that has an entry in the ET. Initialize the AET to be empty.
  3. Repeat until the AET and ET are empty.
    1. Move from ET bucket y to the AET those edges whose \(y_{min} = y\).
    2. Sort the AET on x.
    3. Fill in pixel values on scan-line y using pairs of x coordinates in the AET.
    4. Increment y by 1.
    5. Remove from the AET the entries where \(y = y_{max}\).
    6. For each non-vertical edge in the AET, update \(x = x + 1/m\).

JOGL1_4_3_Triangle implements this in drawtriangle(). With only three edges it's simpler and needs no table, and each pixel on a scan-line gets a random color (W5 p.30, Lesson 5 video).

A convex polygon has all interior angles smaller than 180 degrees. Otherwise it's concave. Convex polygons can be scan-converted faster (W5 p.31). Old OpenGL drew a convex polygon with glBegin(GL_POLYGON) ... glEnd(). Now it only draws triangles, gl.glDrawArrays(GL_TRIANGLES, 0, 3), and any polygon can be cut into triangles. A triangle is always convex (W5 p.31, Lesson 5 video).

Chen's slide figure (the one with edges AB, BC, CD, DE, EF, FA) starts with AB and BC both in bucket 1 at x = 7. In the video he steps AB's x by \(-5/2\) and BC's by \(+3/2\) to get the next row's pair (W5 p.29, Lesson 5 video).

Easy to get wrong

  • "The algorithm only works for convex polygons." Wrong. It fills general polygons by pairing sorted intersections (quiz 5 key, Chen book 1.3). Convex polygons are just faster to scan-convert (W5 p.31).
  • "It builds the AET first, then the ET, then pairs of intersections." Wrong order. ET first from the vertices, then the AET per scan-line, then pairs (quiz 5 key, W5 p.30).
  • "The ET is sorted by the larger y." It's sorted by the smaller y (W5 p.29).
  • "Each edge stores its slope m." It stores \(1/m\), since y steps by 1 and x moves by \(1/m\) (W5 p.30, Lesson 5 video).
  • "Edges are removed when y passes \(y_{min}\)." They're removed when \(y = y_{max}\) (W5 p.30).
  • "Modern OpenGL still has GL_POLYGON." Not in the new pipeline. It only draws triangles (W5 p.31).

Clipping lines, polygons and triangles

The idea

If a primitive sticks out of the window, you keep only the part inside. A line becomes a shorter line with two new endpoints. A polygon becomes a new list of vertices that are all inside (W5 p.32).

You handle one boundary at a time. Against one edge of the window, a line is either all inside (keep it), all outside (drop it), or crossing (cut it at the intersection). Do that for left, right, bottom and top and you're done. Polygons work the same way by walking around their edges. Since the new pipeline only draws points, lines and triangles, you only need a small fixed set of clipping algorithms no matter how complicated the model is.

What to know

Cohen-Sutherland line clipping (W5 p.33). Iterate for l, r, b, t (left, right, bottom, top clip edges). If a segment can be neither trivially accepted nor trivially rejected, divide it at a clip edge so one piece can be trivially rejected. Trivial accept is both endpoints inside, trivial reject is both outside (Lesson 5 video). The 4-bit outcodes from textbooks † aren't on Chen's slides.

Implementation sketch, drawClippedLine calls clip(...) against (l, b, r, t) to get new endpoints, then calls line(...) on them (W5 p.34).

Window clipping in the fragment shader. J1_4_3_windowClipping checks gl_FragCoord.x and .y (device coordinates) against 201 and 600 and paints fragments outside that box dark gray, vec4(0.2,0.2,0.2,1.0) (W5 p.35). Chen calls this a "cheating algorithm" because it uses the hardware per pixel instead of clipping the geometry (Lesson 5 video).

Line against a 3D plane (W5 p.36). Plane \(Ax + By + Cz + D = 0\). Line \(x = x_0 + t(x_1-x_0)\), \(y = y_0 + t(y_1-y_0)\), \(z = z_0 + t(z_1-z_0)\). Substitute the line into the plane and solve for t. Solving gives † (derived, not printed on the slide)

\[t = -\frac{Ax_0 + By_0 + Cz_0 + D}{A(x_1-x_0) + B(y_1-y_0) + C(z_1-z_0)}\]

The plane cuts the world in two and you keep the side you choose (Lesson 5 video).

Sutherland-Hodgman polygon clipping (W5 p.37). Walk the polygon from \(v_1\) to \(v_n\) and back to \(v_1\) against one boundary. Each step adds 0, 1 or 2 vertices to the output list. There are 4 clipping boundaries.

Triangles (W5 p.38). New OpenGL has only triangles. Against one boundary, if two vertices are outside you get one new triangle. If one vertex is outside, the inside part is a quadrilateral, which is cut into two new triangles.

Polygon against a plane (W5 p.39). A polygon is a list of vertices, which is a list of edges (pairs of vertices), so this is essentially line clipping against a plane done per edge.

Point clipping is just an inside test, which is why Chen only talks about two. That reading is my interpretation, so pick the quiz wording if it appears.

Worked example

  1. Edge \(v_1 \to v_2\) goes inside to outside. Add intersection \(i_{12}\).
  2. Edge \(v_2 \to v_3\) goes outside to inside. Add intersection \(i_{23}\), then \(v_3\).
  3. Edge \(v_3 \to v_1\) goes inside to inside. Add \(v_1\).
  4. Output list is \(i_{12}, i_{23}, v_3, v_1\), four vertices. That quadrilateral becomes two triangles, matching "one end point is outside the boundary, two new triangles" (W5 p.37 to 38).

  • "There are so many different models, so we need many different algorithms." Wrong. Every model is built from the same few primitives (quiz 5 key, Lesson 5 video).
  • "It depends on the boundaries, a cube needs a couple of its own algorithms." Wrong. A cube is planes, and clipping against a plane reuses line clipping (quiz 5 key, W5 p.36, 39).
  • "It is not clear how many algorithms we need." Wrong. The answer is at most 3 for each kind of boundary (quiz 5 key).
  • "Cohen-Sutherland always splits the line into exactly two pieces once." It iterates over l, r, b, t and only splits when it can't trivially accept or reject (W5 p.33).
  • "A triangle with one vertex outside gives one triangle." It gives two. Two vertices outside gives one (W5 p.38).
  • "Sutherland-Hodgman outputs the start vertex on in-to-in." It outputs the ending vertex p (W5 p.37).

Characters. Bitmap fonts vs outline fonts

The idea

A character on screen is just a small shape, so the system needs some way to store it. There are two ways. A bitmap font stores each character as a little picture, a rectangle of 0s and 1s. An outline font stores each character as a description, a set of lines and curves, like a tiny model.

Each choice pays for something. A bitmap is fast because drawing it is just copying the rectangle into the framebuffer. But a small bitmap doesn't scale well, so the library has to keep a separate bitmap for every size and typeface, and that takes space. An outline is a set of vertices, so you can scale and rotate it like any other model. The cost is time, because lines and curves have to be scan-converted every time you draw them.

Chen's point for this course is that the built-in text tools (GLUT and TextRenderer) don't work with shaders, so you build characters yourself out of line segments. That's an outline font, and it's exactly what HW6 asks for (Lesson 6 video).

Attributes and pattern anchoring

The idea

An attribute is anything that changes how a primitive looks without changing what it is. A line is still a line whether it's dashed, thick, red or smoothed.

A pattern is an image inside a primitive. The interesting question is what the pattern is pinned to. If you pin it to a vertex of the triangle, the pattern rides along when the triangle moves. If you pin it to the corner of the window, the pattern stays put and the triangle slides over it, so the pattern looks like it's creeping inside the triangle. Chen compares the second case to looking out an airplane window (Lesson 6 video).

What to know

Definition. Any parameter that affects a primitive displayed is an attribute parameter (W6 p.6).

Cap is the shape of the line's end points and join is how two segments meet (Chen textbook 1.4).

Patterns are pixels. They're either generated while scan-converting or copied from a bitmap. Bitmap fonts are themselves patterns (W6 p.7).

At the corner of the drawing area (viewport)The pattern doesn't move with the primitive. It looks like it creeps inside the moving primitive

In JOGL1_4_3_TrianglePattern the pattern is generated in the fragment shader from gl_FragCoord, the pixel's window position (W6 p.8). The uniform sPos is both the anchor and a switch.

uniform int sPos;
out vec4 fColor;
void main(void) {
  if (sPos<300)  // anchor on the window
    fColor = vec4(sin(gl_FragCoord.x/3.14), cos(gl_FragCoord.y/3.14), tan(gl_FragCoord.x/3.14), 1.0);
  else           // anchor on the vertex
    fColor = vec4(sin((gl_FragCoord.x-sPos)/3.14), cos((gl_FragCoord.y-sPos)/3.14), tan((gl_FragCoord.x-sPos)/3.14), 1.0);
}

Why this works. With the window anchor, a pixel's color depends only on its screen position, so it's fixed to the window. With the vertex anchor, the color depends on the position relative to sPos, and sPos moves with the triangle, so the pattern moves too (Lesson 6 video). In the Java code sPos is the average x of the three vertices, (v[0][0]+v[1][0]+v[2][0])/3, which Chen calls the center of the triangle (Lesson 6 video). The pattern is cut at the triangle's boundary because only pixels inside the primitive get fragments.

Small mismatch. The shader file in JOGL2020 uses 500 and 6.28 where the slide shows 300 and 3.14. Same idea, different constants. Quote the slide on a quiz.

  • "A pattern is the outline of a primitive." No. On the quiz a pattern matches "images inside primitives" (W6 p.7, Lesson 6 video).
  • "Primitives" in the matching question means lines or triangles, the things being drawn, not the patterns or pixels.
  • "Polygons have cap and join attributes." Those are listed under line attributes only (W6 p.6).

Antialiasing. Supersampling and area sampling

The idea

Pixels are discrete, so a slanted line comes out as a staircase. That's aliasing. One fix is more pixels, a higher screen resolution. The other fix is antialiasing, which keeps the same pixels but gives them in-between intensities. Pixels near the center of the line get mostly foreground color, pixels near the edge get mostly background color, and your eye reads the result as smooth (Lesson 6 video).

The methods differ in how they decide "how much of this pixel is in the line." Supersampling checks several sample points inside the pixel and counts how many fall in the line. Area sampling treats the line as a rectangle and measures the overlap area. Weighted area sampling also cares where in the pixel the overlap is, so area near the pixel's center counts more.

What to know

Higher resolutionNot antialiasing, just more pixels so the steps are smaller (W6 p.9)

Chen's picture of weighted area sampling is a cone or Gaussian "bun" sitting on the pixel. The line's edges cut through it, and the volume inside the line sets the intensity. He jokingly calls it "volume sampling," a name he says isn't in textbooks (Lesson 6 video). The book adds that the cone's base can be bigger than the pixel, so a line can affect a pixel it doesn't touch (Chen textbook 1.4.1).

Supersampling trades accuracy for speed. More samples is more accurate but slower (Lesson 6 video). Antialiasing in general is slow, which is why most systems skip it by default (Lesson 6 video).

The simple intensity equation for a 3-pixel-wide line, where \(D\) is the pixel's distance to the line's center (W6 p.13).

\[ (r,g,b)\cdot\left(1-\frac{D}{1.5}\right) \qquad\text{and with a background}\qquad F\left(1-\frac{D}{1.5}\right) + B\,\frac{D}{1.5} \]

Why 1.5. For a 3-pixel-wide line the farthest pixel center is 1.5 from the center line, so \(D=1.5\) gives pure background and \(D=0\) gives pure foreground (Lesson 6 video). For a 5-pixel line the farthest is 2.5, and Chen's JOGL code divides by 2.5 (Lesson 6 video, JOGL1_4_4_aLine.java).

IntensifyPixel takes the absolute value first, if (D<0) D = -D;, because negative \(D\) only means the pixel is above the line (W6 p.15).

Worked example

  1. Red line \(F=(1,0,0)\) on a blue background \(B=(0,0,1)\). A pixel has \(D=0.6\).
  2. Foreground weight \(1-0.6/1.5 = 0.6\). Background weight \(0.6/1.5 = 0.4\).
  3. Color \(=0.6(1,0,0)+0.4(0,0,1) = (0.6,\,0,\,0.4)\).
  4. On a black background the second term is zero, so the pixel is just \((0.6,0,0)\). That's why the slide code only needs \(r\cdot(1-D/1.5)\) (W6 p.15).
  5. Same pixel in the 5-pixel JOGL version gives \(1-0.6/2.5 = 0.76\) brightness.

Easy to get wrong

  • "Supersampling is prefiltering." No. Supersampling is postfiltering and area sampling is prefiltering (W6 p.10, W6 p.11).
  • "Unweighted area sampling weights area near the center more." That's weighted. Unweighted uses the overlap area only, the box filter (W6 p.11, W6 p.12).
  • "An intensity table works for any line width." No. The table changes with the line width, which is the stated problem (W6 p.12).
  • "Higher resolution is an antialiasing algorithm." The slide lists it as a separate way to reduce jaggies (W6 p.9).
  • "\(D=1.5\) gives full foreground." Backwards. \(D=0\) is on the center line and keeps full foreground. \(D=1.5\) gives zero foreground (W6 p.13).

Distance to the line by counting sin a and cos a

The idea

To use the intensity equation you need \(D\) for every pixel. Computing a point-to-line distance from scratch each time is slow. Chen's trick is that, like the midpoint line algorithm, the distance can be updated step by step. Moving one pixel east changes the distance by \(\sin a\). Moving one pixel north changes it by \(\cos a\). Here \(a\) is the angle of the line with the x axis.

The sign comes from which side of the line you end up on. Chen's \(D\) is positive below the line and negative above it (Chen textbook 1.4.2, W6 p.15 comment). Going east on a line with slope between 0 and 1 moves you toward the lower side, so \(D\) grows. Going north moves you toward the upper side, so \(D\) shrinks.

What to know

The single-step updates from Chen's figure (W6 p.14, Chen textbook Fig. 1.4).

NeighborDistance
East\(D_E = D + \sin a\)
West\(D_W = D - \sin a\)
North\(D_N = D - \cos a\)
South\(D_S = D + \cos a\)
Northeast\(D_{NE} = D_E - \cos a = D + \sin a - \cos a\)

The theorem on the slide is that, given \(D\), any other pixel's distance comes from counting \(\sin a\) for each step left or right and \(\cos a\) for each step up or down (W6 p.14). So for a pixel \(M\) steps east and \(N\) steps north,

\[ D_{M,N} = D + M\sin a - N\cos a . \]

In the algorithm, \(\sin a = dy/\sqrt{dx^2+dy^2}\) and \(\cos a = dx/\sqrt{dx^2+dy^2}\), and smc_a = sin_a - cos_a is precomputed for the NE step (W6 p.16).

while (x<xn+1) {
  IntensifyPixel(x,y,D);          // current pixel
  IntensifyPixel(x,y+1,D-cos_a);  // North
  IntensifyPixel(x,y-1,D+cos_a);  // South
  x++;
  if (d<=0) { D+=sin_a; d+=incrE; }          // went E
  else { D+=smc_a; y++; d+=incrNE; }        // went NE
}

This is the midpoint (Bresenham) loop with three extra lines. Each column draws three pixels (center, north, south), which is the 3-pixel-wide line (W6 p.16). The book notes \(|D|\le 0.5\) for the pixel Bresenham picks, so the N and S pixels are at most 1.5 away (Chen textbook 1.4.2). The JOGL version draws five pixels per column with \(D\pm\cos a\) and \(D\pm 2\cos a\) (Lesson 6 video).

Side note on the code. JOGL1_4_4_aLine.java labels y-1 as "N pixel" with D-cos_a, the opposite row from slide 16, after its own coordinate flips. On a quiz, follow slide 16 and the figure, where North is \(y+1\) and gets \(D-\cos a\) (W6 p.16).

Chen also says the hardware antialiasing isn't perfect, since the JOGL version keeps converting between physical (pixel) and logical coordinates, and he floats computing \(D\) in the fragment shader instead "just a thought" (W6 p.17).

Worked example

  1. Set up Chen's sign convention. Take a line through the origin at angle \(a\), with unit direction \((\cos a, \sin a)\). The signed distance of a point \((x,y)\) is \(D(x,y) = x\sin a - y\cos a\). This is positive below the line and negative above it, which matches Chen's "distances from the pixels above the line are negatively labeled" (Chen textbook 1.4.2).
  2. One step east. \(D(x+1,y) = D(x,y) + \sin a\). The sign is plus because, for \(0\le a\le 45^\circ\), stepping right takes you further under the rising line.
  3. One step north. \(D(x,y+1) = D(x,y) - \cos a\). The sign is minus because stepping up takes you toward or past the line to its upper side.
  4. M east and N north. \(D\) is linear in \(x\) and \(y\), so the steps just add up. \(D(x+M, y+N) = D + M\sin a - N\cos a\). That's the quiz key, written \(D - N\cos a + M\sin a\).
  5. Matching letters to roles. The question says "m_th to the east and n_th to the north" in lower case, and the options use capital \(M\) and \(N\) for the same numbers. East pairs with \(\sin a\) and north pairs with \(\cos a\). Nothing is swapped. The easy slip is to remember "cos for up" but flip the signs, which gives \(D + N\cos a - M\sin a\), the answer he chose on attempt 1. That one has both signs backwards.
  6. Numeric check. Line from \((0,0)\) to \((4,3)\), so \(\sin a = 3/5 = 0.6\) and \(\cos a = 4/5 = 0.8\). Start at pixel \((1,1)\). Direct distance is \(|3\cdot1-4\cdot1|/5 = 0.2\) and the pixel is above the line, so \(D=-0.2\).
  7. Go \(M=2\) east, \(N=0\) to pixel \((3,1)\). Key gives \(-0.2 + 2(0.6) = 1.0\). Direct is \(|9-4|/5 = 1.0\), below the line, so \(+1.0\). Match. The wrong option gives \(-0.2 - 1.2 = -1.4\), magnitude 1.4, which is wrong.
  8. Go \(M=3\), \(N=2\) to pixel \((4,3)\), which is the line's endpoint. Key gives \(-0.2 + 3(0.6) - 2(0.8) = 0\). Correct, it's on the line. The wrong option gives \(-0.2 + 1.6 - 1.8 = -0.4\).
  9. Go \(M=1\), \(N=1\) (the NE step) to \((2,2)\). Key gives \(-0.2 + 0.6 - 0.8 = -0.4\). Direct is \(|6-8|/5 = 0.4\), above the line, so \(-0.4\). This is the slide's \(D_{NE} = D+\sin a-\cos a\) (W6 p.14).

Easy to get wrong

  • "\(D + N\cos a - M\sin a\)." Both signs flipped. North subtracts \(\cos a\) and east adds \(\sin a\) (W6 p.14). This was his attempt-1 answer.
  • "\(D - N\cos a - M\sin a\)." East would make the distance smaller, which contradicts \(D_E = D+\sin a\) (W6 p.14).
  • "East adds \(\cos a\)." No. Horizontal steps count \(\sin a\) and vertical steps count \(\cos a\) (W6 p.14). Think of it this way. For a flat line (\(a=0\)), moving east doesn't change the distance at all, and \(\sin 0 = 0\).
  • "The South pixel is \(D+\sin a\)." Chen says this once in the video by mistake, but the slide code and the book both use \(D+\cos a\) for South (W6 p.16, Chen textbook Fig. 1.4).
  • "The NE update is \(D + \cos a - \sin a\)." It's \(D + \sin a - \cos a\), stored as smc_a (W6 p.16).

Frame rate vs refresh rate

The idea

Two different things run at their own speeds. Your program draws frames into the framebuffer. The video controller reads the framebuffer and paints the display. Drawing faster than the display refreshes buys nothing, because the extra frames never get shown.

Drawing a circle by subdividing triangles

The idea

Start with four triangles that share the center and meet the unit circle at (1,0), (0,1), (−1,0) and (0,−1). That's a square. Now treat the two outer vertices of a triangle, \(v_1\) and \(v_2\), as vectors. Their sum points exactly halfway between them, but it's too long. Normalize it back to length 1 and you get a new point \(v_{12}\) on the circle. Replace the one triangle with two, \((v_1, v_{12})\) and \((v_{12}, v_2)\), and repeat. Each round doubles the triangles and the shape gets rounder (W6 p.19).

Chen admits it's not the best way to draw a circle. He uses it because raising the center turns the same structure into a cone, and later into cylinders and spheres (Lesson 6 video).

What to know

\(v_{12} = \mathrm{normalize}(v_1+v_2)\), where \(v_1+v_2 = (v_{1x}+v_{2x},\, v_{1y}+v_{2y},\, v_{1z}+v_{2z})\) and after normalizing \(|v_1|=|v_2|=|v_{12}|\) (W6 p.19).

Length and normalize. \(|v| = \sqrt{x^2+y^2+z^2}\). Normalizing divides each component by the length to get a unit vector. Chen's normalize() prints an error and returns if the length is 0, since you can't divide by zero (JOGL1_4_5_Circle.java).

v12[0] = v1[0] + v2[0]; v12[1] = v1[1] + v2[1]; v12[2] = v1[2] + v2[2];
normalize(v12);
subdivideCircle(vPoints, radius, v1, v12, depth - 1);
subdivideCircle(vPoints, radius, v12, v2, depth - 1);

At depth == 0 it stops and stores one triangle \((v_1, v_2, \text{origin})\) in vPoints, scaled by 2*radius/WIDTH. Nothing is drawn inside the recursion. All triangles go into one array, sent through a VBO and drawn with one glDrawArrays(GL_TRIANGLES, ...) (W6 p.20, Lesson 6 video).

Triangle count. One call to subdivideCircle with depth \(d\) produces \(2^d\) triangles (W6 p.19). drawCircle calls it four times, once per starting triangle, so the screen shows \(4\cdot 2^d\), and the array is sized 4*(int)Math.pow(2,depth) triangles times 3 vertices times 3 floats (JOGL1_4_5_Circle.java). That's why the slide says depth 0 draws 4 triangles and depth 1 draws 8 (W6 p.19). The demo cycles depth from 0 to 6 with depth % 7.

Vertex shader details (W6 p.21). It rotates with rotate_y*rotate_z using the uniform theta (rotations are covered later, W6 p.22). The color is normalize(iPosition) with abs() on each part, except the center vertex (0,0,0) gets gray (0.5, 0.5, 0.5) because normalizing a zero-length vector fails. Chen says the program just crashed or went white until he caught that (Lesson 6 video). Color comes from the original position, so rotation doesn't change it (Lesson 6 video).

Worked example

  1. \(v_1=(1,0,0)\), \(v_2=(0,1,0)\). Sum is \((1,1,0)\), length \(\sqrt2\approx1.414\). Normalized \(v_{12}\approx(0.7071,\,0.7071,\,0)\), the 45° point on the circle.
  2. Next level between \((1,0,0)\) and \((0.7071,0.7071,0)\). Sum \((1.7071,0.7071,0)\), length \(\approx1.8478\). Normalized \(\approx(0.9239,\,0.3827,\,0)=(\cos22.5^\circ,\sin22.5^\circ)\). Still on the circle, halfway in angle.
  3. Triangles from one starting triangle, depth 0 to 6. \(2^d\) = 1, 2, 4, 8, 16, 32, 64. This is the quiz answer.
  4. Whole circle (four starting triangles). \(4\cdot2^d\) = 4, 8, 16, 32, 64, 128, 256. At depth 3 that's 32 triangles, 96 vertices, 288 floats in vPoints.

Easy to get wrong

  • "Subdivide by averaging the two vertices." Averaging gives the midpoint of the chord, which is inside the circle. You add the two vectors and normalize (W6 p.19). The quiz phrase is "add the two edges as vectors and normalize the result."
  • "Number of triangles after depth recursions is \(2\cdot depth\)" or "\(depth^2\)." It doubles every level, so \(2^{depth}\) (W6 p.19). The \(4\cdot2^{depth}\) total only applies if the question counts all four starting triangles.
  • "Normalize gives the length." No. \(\sqrt{x^2+y^2+z^2}\) is the length, normalize gives a unit vector (W6 p.19, quiz 6 matching).
  • "normalize() works on any vector." Not a zero vector. That's why the shader special-cases the center (W6 p.21).

OpenGL primitives

The idea

OpenGL only really draws three things. Points, lines and triangles. Every fancy mode in the list is just a different way of handing it vertices for one of those three. A triangle strip or fan saves you from repeating shared vertices, but what comes out the other end is still triangles.

Chen's reason for caring is clipping. Because there are only three primitive types, the system only needs three clipping algorithms for each clipping boundary. Curves, surfaces, spheres and anything else get approximated by these three (W7 p.4).

What to know

The modern call is gl.glDrawArrays(GL_POINTS, 0, 3), where the first argument picks the primitive, the second is the starting vertex and the third is the vertex count (W7 p.3).

The modes listed for glDrawArrays are GL_POINTS, GL_LINE_STRIP, GL_LINE_LOOP, GL_LINES, GL_LINE_STRIP_ADJACENCY, GL_LINES_ADJACENCY, GL_TRIANGLE_STRIP, GL_TRIANGLE_FAN, GL_TRIANGLES, GL_TRIANGLE_STRIP_ADJACENCY, GL_TRIANGLES_ADJACENCY and GL_PATCHES (W7 p.3). Chen says the adjacency modes are for drawing curves and curved surfaces (Lesson 7 video).

The old way was glBegin(mode) ... glEnd(), with extra modes GL_POLYGON (a simple convex polygon), GL_QUADS and GL_QUAD_STRIP (W7 p.5). Chen calls it obsolete but says old code still compiles and runs, so you'll see it (Lesson 7 video).

Color used to be a state set with glColor3f(r, g, b) that stuck for every object drawn after it (W7 p.6). In OpenGL 4.x colors are attached to vertices in a VAO/VBO, and a fragment's color is interpolated from the primitive's vertex colors (W7 p.6).

Worked example

  1. You want two triangles sharing an edge, with vertices 1, 2, 3, 4.
  2. With GL_TRIANGLES you send 6 vertices, 1, 2, 3 and then 2, 3, 4 (or 2, 4, 3).
  3. With GL_TRIANGLE_STRIP you send just 1, 2, 3, 4. The rule is \(n\) vertices give \(n-2\) triangles, so \(4-2=2\). Chen's point is that it "saves a little bit" (Lesson 7 video).

Easy to get wrong

  • "Spheres are an OpenGL primitive." Wrong. The primitives are points, lines and triangles, and a sphere is built out of triangles by subdivision (W7 p.4, W7 p.26). This was a distractor on Quiz 7.
  • "A triangle strip draws something other than triangles." Wrong. Strips and fans are just a cheaper way to list vertices for triangles (Lesson 7 video).
  • "glColor3f is how you color vertices in modern OpenGL." Not in 4.x. Colors go through the VAO/VBO into the shaders (W7 p.6).

The depth buffer (z-buffer) and hidden-surface removal

The idea

Once you draw in 3D, things block each other. If you just paint triangles in the order you send them, whatever gets drawn last wins, even if it's behind something. The z-buffer fixes this. Next to the color buffer there's a second buffer, the same size, holding one number per pixel. That number is how far away the closest thing drawn at that pixel so far is.

Every time a new pixel of a polygon wants to be drawn, the system compares its depth with what's stored. If the new pixel is closer, it overwrites both the depth and the color. If not, it's thrown away. After all polygons are drawn, the color buffer only holds the visible surfaces, no matter what order the polygons came in.

What to know

The color buffer (front or back) stores RGBA per pixel. The depth buffer is the same size and stores one depth value (z) per pixel, the distance from that pixel to the eye. The point on a primitive closest to the viewpoint is the one that's visible (W7 p.7).

If no model covers a pixel, its depth value is whatever it was cleared to, which by default is the back clipping plane. glClearDepth(depth) sets that clear value. The default is 1, the back clipping plane (farthest), and values are clamped to [0, 1] (W7 p.9). Chen describes 0 as the eye side or front and 1 as the far end (Lesson 7 video).

OpenGL setup (W7 p.8, W7 p.13).

// once, in init()
gl.glEnable(GL.GL_DEPTH_TEST);
// every frame, in display()
gl.glClear(GL.GL_COLOR_BUFFER_BIT | GL.GL_DEPTH_BUFFER_BIT);
// turn hidden-surface removal off
gl.glDisable(GL.GL_DEPTH_TEST);

You can clear the two buffers in two separate glClear calls or OR the bits together in one (W7 p.13). Enabling the depth test is what invokes the z-buffer algorithm. Without it, the result depends on which polygon was drawn first (Lesson 7 video). If you forget to clear the depth buffer every frame, old close depths stay in it and block the new frame, so the object gradually disappears (Lesson 7 video).

What glClear does, in Chen's pseudocode, is loop over every pixel, write the clear color into the color buffer and write the back clipping plane depth into the depth buffer (W7 p.10).

The algorithm itself (W7 p.11).

for (each polygon)
  for (each pixel (x,y) in the polygon scan-conversion)
    if (GL_DEPTH_TEST enabled) zBuffer(x,y);
    else draw_frameBuffer(x,y);

zBuffer(x, y) {
  pixelDepth = polygon's z-value at (x,y);
  if (pixelDepth < read_depthBuffer(x,y)) {
    draw_depthBuffer(x, y, pixelDepth);
    draw_frameBuffer(x, y);
  }
}

Getting the pixel's z (W7 p.12). For a line, \(z = z_0 + (z_1 - z_0)t\). For a polygon with plane equation \(Ax + By + Cz + D = 0\), \[ z = f(x,y) = -\frac{Ax + By + D}{C} \] and along one scan line you just add a constant each step, \(z_{i+1} = z_i + d\) with \(d = -A/C\). So scan-conversion is 2D drawing, but each pixel carries a 3D z value that's compared with the z-buffer before writing to the framebuffer (W7 p.12).

Chen says many hidden-surface algorithms existed and the z-buffer "won the competition" and is now done in hardware (Lesson 7 video).

Displaying the depth buffer as an image isn't on the slides but Quiz 7 asked about it. The key treats it as a gray image of the same visible surface you see in the color buffer, where darker means closer (depth near 0 is black, depth 1 at the back plane is white). It only stores the nearest surface per pixel, so hidden surfaces are gone and can't be rebuilt from it.

Worked example

  1. Clear. Pixel (10, 20) gets the background color and depth 1.0 (W7 p.9 to 10).
  2. Polygon A covers that pixel at depth 0.6. Since \(0.6 < 1.0\), the depth becomes 0.6 and the pixel takes A's color.
  3. Polygon B arrives at depth 0.4. Since \(0.4 < 0.6\), B is closer. Depth becomes 0.4 and the pixel takes B's color.
  4. Polygon C arrives at depth 0.8. Since \(0.8\) is not less than \(0.4\), C is behind B and nothing is written.
  5. Final pixel shows B with depth 0.4. Drawing in the order C, A, B or any other order ends the same way. With the depth test disabled the pixel would show C, the last one drawn.
  6. Pixel depth from a plane. For \(x + y + z - 1 = 0\) (so \(A=B=C=1, D=-1\)) at \((0.2, 0.3)\), \(z = -(0.2 + 0.3 - 1)/1 = 0.5\) (W7 p.12).

Easy to get wrong

  • "A depth-buffer pixel value is the color or intensity of the model at that pixel." Wrong. The color lives in the color buffer. The depth buffer holds a distance (W7 p.7). Quiz 7 distractor.
  • "A depth-buffer value is the distance to some model that may not be at that pixel." Wrong. It's the closest distance of the models at that very pixel (W7 p.7). Quiz 7 distractor.
  • "An empty pixel has depth 0." Wrong. An empty pixel keeps the cleared value, the back clipping plane, which defaults to 1 (W7 p.9). Quiz 7 counted "distance to the back-clipping plane" as correct.
  • "You can reconstruct the full 3D model, hidden parts included, from the color and depth buffers." Wrong. Only the nearest surface per pixel survives the z-buffer test, so the hidden surfaces are gone (W7 p.11). Quiz 7 distractor.
  • "Enable the depth test and you're done." You also have to clear the depth buffer every frame, or the old values block new drawing (W7 p.8, Lesson 7 video).
  • "The z-buffer test keeps the pixel with the larger depth." Wrong direction. It writes when pixelDepth < read_depthBuffer(x,y), so smaller (closer) wins (W7 p.11).
  • The depth-image question on Quiz 7 was ungraded (0/0), and its key also marks "the depth-buffer image and color-buffer image are the same, but the depth one is gray" as correct. Read that as "same visible shapes in gray." Strictly the gray levels encode distance, not the model's color, so the key may be shaky there.

Polygon faces, normals, polygon mode and culling

The idea

A triangle has two sides. Which side is the front is decided by its normal, a vector perpendicular to the surface. And the normal's direction comes from the order you list the vertices in. Curl the fingers of your right hand around the vertices in order. Your thumb points along the normal. Counterclockwise as seen from where you stand means the normal points at you (W7 p.14).

If the normal points toward the viewer, the polygon is front-facing. If it points away, it's back-facing. Chen's basketball picture helps. From outside you see the front of half the ball. Cut it in half and look inside and you're seeing back faces (Lesson 7 video).

Culling just means "don't even rasterize these faces." It's mainly for speed, since the back faces of a closed object are hidden anyway, but it can also be used for effects like seeing inside an object (Lesson 7 video).

What to know

Front-facing means the normal points toward the viewer. Back-facing means it points away. The order of vertices decides the normal direction (W7 p.14).

With the eye on the positive z axis, front-facing means the angle between the normal and the z axis is under 90 degrees, so the dot product of the normal with \((0,0,1)\) is positive, because \(\cos 90^\circ = 0\) and angles past 90 give a negative cosine (Lesson 7 video).

glPolygonMode(face, mode). The face is GL_FRONT_AND_BACK, GL_FRONT or GL_BACK. The mode is GL_POINT, GL_LINE (wireframe) or GL_FILL (W7 p.15). Chen says the default is fill (Lesson 7 video).

glCullFace(mode) says which polygons get discarded and not rasterized. The mode is GL_FRONT, GL_BACK or GL_FRONT_AND_BACK, and it only takes effect after glEnable(GL_CULL_FACE) (W7 p.15). Culling GL_FRONT_AND_BACK draws nothing at all (Lesson 7 video).

gl.glPolygonMode(GL.GL_FRONT_AND_BACK, GL_FILL); // filled
// gl.glPolygonMode(GL.GL_FRONT_AND_BACK, GL_LINE); // wireframe
gl.glEnable(GL_CULL_FACE);
gl.glCullFace(GL_FRONT); // you see the back-facing triangles
// gl.glCullFace(GL_BACK); // you see the front-facing triangles

That's from JOGL2_5_Cone (W7 p.16). Chen's warning is that culling only behaves if every triangle's vertices are listed in a consistent order, so when you build a cone or cylinder you have to get the winding right (Lesson 7 video).

Ways to get a normal (Quiz 7 key, textbook 2.3.3).

Worked example

  1. Triangle with vertices in order \(P_1=(1,0,0)\), \(P_2=(0,1,0)\), \(P_3=(0,0,1)\). The eye is on the positive z axis.
  2. Edges. \(\mathbf{a} = P_2 - P_1 = (-1, 1, 0)\) and \(\mathbf{b} = P_3 - P_1 = (-1, 0, 1)\).
  3. Cross product. \(x = 1\cdot1 - 0\cdot0 = 1\), \(y = 0\cdot(-1) - (-1)\cdot1 = 1\), \(z = (-1)\cdot0 - 1\cdot(-1) = 1\). So \(\mathbf{n} = (1, 1, 1)\).
  4. Facing test. \((1,1,1)\cdot(0,0,1) = 1 > 0\), so the normal points toward the viewer and the triangle is front-facing. It survives glCullFace(GL_BACK) and gets removed by glCullFace(GL_FRONT).
  5. Swap the order to \(P_1, P_3, P_2\). Now \(\mathbf{b}\times\mathbf{a} = (-1,-1,-1)\), the dot product is \(-1\), and the same triangle is back-facing. Same points, opposite winding, opposite face (W7 p.14).
  6. Check with the plane equation. All three points satisfy \(x + y + z - 1 = 0\), whose coefficients give \((1,1,1)\), the same direction. A plane equation fixes the normal only up to sign, since multiplying the equation by \(-1\) describes the same plane.
  7. Chen's cylinder side triangle, listed as v1, v2, v22 with \(v_1=(1,0,0)\), \(v_2=(0,1,0)\), \(v_{22}=(0,1,1)\), gives \((v_2-v_1)\times(v_{22}-v_1) = (-1,1,0)\times(-1,1,1) = (1,1,0)\). That points outward from the z axis, so the outside of the cylinder is the front face, which is why back-face culling leaves the outside visible.

  • "A polygon faces you when it's not upside down." Wrong. Facing is about the normal pointing toward the viewpoint, not about rotation in the image (W7 p.14). Quiz 7 distractor.
  • "glCullFace(GL_FRONT) shows the front faces." Backwards. Cull means discard, so culling GL_FRONT leaves the back-facing triangles (W7 p.16).
  • "glCullFace works on its own." It does nothing until glEnable(GL_CULL_FACE) (W7 p.15).
  • "glPolygonMode(GL_FRONT, GL_LINE) affects every polygon." Only front-facing ones. Use GL_FRONT_AND_BACK to cover both (W7 p.15).
  • "Vertex order doesn't matter for a triangle." It decides the normal, so it decides front versus back (W7 p.14).
  • Quiz 7's facing question was ungraded (0/0). Circle, cone and cylinder by subdivision

The idea

Everything starts from the circle trick in earlier weeks. Take two unit vectors on the circle, add them, normalize the sum, and you get a new point on the circle halfway between. Recurse and the polygon gets closer and closer to a circle (W7 p.18).

The 3D shapes are small edits to that. Lift the center up the z axis and each wedge triangle becomes a slanted side, which gives a cone. Copy the rim up to z = 1 and join the two rims with rectangles (two triangles each), which gives a cylinder (W7 p.17, W7 p.24 to 25). Chen's framing is that these build on each other, so if you get the circle you get the rest (Lesson 7 video).

What to know

Circle (W7 p.18). Start with 4 triangles at depth 0. At depth 1 each splits into 2, so 8. The recursion makes \(2^{\text{depth}}\) triangles per starting triangle, so \(4\cdot 2^{\text{depth}}\) total. The new vertex is \(v_{12} = \text{normalize}(v_1 + v_2)\), and \(|v_1| = |v_2| = |v_{12}|\).

Cone (W7 p.19, W7 p.21). At depth 0, store the side triangle (v1, v2, v0) with the tip v0[2] = 1 on the z axis. Chen's JOGL2_5_Cone also stores a bottom cover at z = 0, so it sizes the array as 2*4*(int)Math.pow(2,depth) triangles. Skip the bottom and you see inside the cone (Lesson 7 video).

if (depth==0) {
  v0[2] = 1; // tip on the z axis
  // store v1, v2, v0 into vPoints
  return;
}
for (int i = 0; i<3; i++) v12[i] = v1[i]+v2[i];
normalize(v12);
subdivideCone(vPoints, v1, v12, depth-1);
subdivideCone(vPoints, v12, v2, depth-1);

Cylinder (W7 p.24 to 25). Draw a circle at z = 0 and another at z = 1, then connect matching rim vertices with rectangles. In code each depth-0 call stores the bottom triangle (v2, v1, v0) and the side rectangle as two triangles (v1, v2, v22) and (v1, v22, v11), where v11 and v22 are v1 and v2 lifted to z = 1. That's 3 triangles per wedge, so the array is sized 3*4*(int)Math.pow(2,depth). Chen's version has no top cover. He says you'd add it as the triangle v11, v22, v0 with the center lifted, and that the array then needs room for more triangles or it crashes (Lesson 7 video).

Viewing volume (W7 p.19 to 20, W7 p.25). The default volume is the cube from -1 to 1 on x, y and z. To use pixel-sized coordinates Chen calls his own myOrtho(left, right, bottom, top, near, far), which defines a box aligned with the axes, for example myOrtho(-w/2, w/2, -h/2, h/2, -w, w) in reshape(). The model has to sit inside the box, including in z, or it gets clipped. The details of this matrix come in later weeks.

Instancing (W7 p.22 to 23). gl.glDrawArraysInstanced(GL_TRIANGLES, 0, vBuf.limit()/3, instances) draws the same model many times. In the vertex shader the built-in gl_InstanceID tells each vertex which copy it belongs to, and JOGL2_6_ConeInstancing uses it (plus a CurTime uniform) to build a different transform for each copy. Without different transforms all copies land in the same spot and look like one (Lesson 7 video). Chen calls this extra information that isn't used often (Lesson 7 video).

Worked example

  1. Circle at depth 3. \(4\cdot 2^3 = 32\) triangles, so 32 sides on the rim.
  2. Cone at depth 3 with a bottom. Sides 32 plus bottom 32 is \(2\cdot4\cdot2^3 = 64\) triangles.
  3. Cylinder at depth 3 the way Chen's code builds it. Per wedge 1 bottom triangle plus 2 side triangles, so \(3\cdot4\cdot2^3 = 96\) triangles. This is the depth Mohamed's HW7 used.
  4. Midpoint check. \(v_1=(1,0,0)\), \(v_2=(0,1,0)\). Sum \((1,1,0)\), length \(\sqrt2\), so \(v_{12} = (0.707, 0.707, 0)\), which has length 1 and is on the unit circle.

Easy to get wrong

  • "Circle subdivision multiplies triangles by 4 each level." No, that's the sphere. The circle splits each triangle into 2, so it's \(4\cdot 2^{\text{depth}}\) (W7 p.18).
  • "\(v_1 + v_2\) is already on the circle." Only after normalizing. Without it the point sits inside the circle (W7 p.18).
  • "A cone is made by raising the rim." The cone raises the center. The cylinder raises the rim (a second circle) (W7 p.17).
  • "The model can be anywhere once you call myOrtho." It still has to lie inside the box you specify, z included, or it's clipped (W7 p.19, W7 p.25).
  • "glDrawArraysInstanced automatically spreads copies out." It doesn't. You transform each copy yourself using gl_InstanceID in the shader (W7 p.23).

Sphere from an octahedron

The idea

Same trick, one dimension up. An octahedron has 8 triangular faces, 4 on top and 4 underneath, and all 6 of its corners sit on the unit sphere. Take one face \(v_1, v_2, v_3\). Add each pair of corners and normalize, and you get three new points that are also on the sphere. Those six points form four smaller triangles, and the four together hug the sphere better than the one flat face did (W7 p.26).

Repeat on every small triangle and it quickly looks round. Each level multiplies the triangle count by 4.

What to know

Triangle \((v_1, v_2, v_3)\) on a sphere with \(|v_1|=|v_2|=|v_3|=1\). Then \(v_{12} = \text{normalize}(v_1+v_2)\) is on the sphere too, and the triangle splits into 4 (W7 p.26).

if (depth==0) { /* store v1, v2, v3 */ return; }
for (int i = 0; i<3; i++) {
  v12[i] = v1[i]+v2[i]; v23[i] = v2[i]+v3[i]; v31[i] = v3[i]+v1[i];
}
normalize(v12); normalize(v23); normalize(v31);
subdivideSphere(vPoints, v1, v12, v31, depth-1);
subdivideSphere(vPoints, v2, v23, v12, depth-1);
subdivideSphere(vPoints, v3, v31, v23, depth-1);
subdivideSphere(vPoints, v12, v23, v31, depth-1);

Bounding volumes, minmax testing and collision detection

The idea

Real models are thousands of triangles, so checking them against each other directly is slow. Instead, wrap each model in something simple, like a box or a sphere, and do the math on the wrappers. That's a bounding volume.

Before z-buffer hardware, bounding boxes were used for hidden-surface removal. Sort the boxes by z and draw from farthest to closest, so near things paint over far things. Chen says this is basically obsolete for hiding surfaces, but bounding volumes are still how collision detection works today, like a plane hitting a building or two cars in a racing game (Lesson 7 video).

What to know

Minmax testing (W7 p.28). Viewpoint at the origin, models along the negative z axis. Bound each model with a box whose faces are perpendicular to x, y or z. Compare the boxes' minimum and maximum z bounds to decide which model to render first, and render from farthest to closest. Using bounding volumes to decide rendering priority is called minmax testing.

Collision detection (W7 p.29). It stops two animated models from penetrating each other. Bounding volumes make the distance check fast. The volume can be a sphere instead of a box to make the math simpler. Using several spheres of different radii fits a model better, but the collision check gets more complex.

Sphere rule. Two spheres with centers \(C_1, C_2\) and radii \(r_1, r_2\) collide when \[ |C_1 C_2| < r_1 + r_2 \] and are apart when the center distance is bigger than the sum of the radii (Lesson 7 video, textbook 2.3.4). The distance is \(\sqrt{(x_2-x_1)^2 + (y_2-y_1)^2 + (z_2-z_1)^2}\). † Exactly equal means they just touch. † Comparing squared distance with \((r_1+r_2)^2\) avoids the square root. Neither of these is on the slides.

A sphere suits a ball-shaped model. For something long like a sword one sphere fits badly, which is why you'd use several (Lesson 7 video).

Worked example

  1. Sphere A at \(C_1=(0,0,0)\) with \(r_1 = 2\). Sphere B at \(C_2=(3,4,0)\) with \(r_2 = 4\).
  2. Center distance. \(\sqrt{3^2 + 4^2 + 0^2} = \sqrt{25} = 5\).
  3. Sum of radii. \(2 + 4 = 6\).
  4. \(5 < 6\), so they overlap by 1 unit. Collision.
  5. Shrink B to \(r_2 = 2\). The sum is 4, and \(5 > 4\), so there's a gap of 1 unit. No collision.
  6. Squared version †. \(25 < 36\) gives the same answer for the first case without a square root.

Easy to get wrong

  • "They collide when the center distance is bigger than the sum of the radii." Backwards. Bigger than the sum means there's a gap between them (textbook 2.3.4). Mohamed picked this on attempt 1 of Quiz 7 and lost the full 10 points.
  • "They collide when the center distance is bigger than one of the radii." That compares against the wrong quantity. One radius says nothing about where the other sphere's surface is (W7 p.29). Quiz 7 distractor.
  • "We may not have enough information to decide." For two spheres, two centers and two radii are all you need (Lesson 7 video). Quiz 7 distractor.
  • "Minmax testing renders closest first." It renders farthest to closest so closer models paint over (W7 p.28).
  • "More spheres per model makes collision detection simpler." It makes the bound more accurate but the computation more complex (W7 p.29).

What the assignment practiced

The idea

Programming Assignment 7 asked for a cylinder that demonstrates wireframe and solid, the depth buffer enabled and disabled, and front-face and back-face culling, submitted as a zip (W7 p.30). In the lecture Chen says to modify his cylinder program the way he played with the cone, and suggests showing one effect for several seconds and then the next (Lesson 7 video).

Mohamed's mshaik5_2_6_Cylinder.java keeps Chen's subdivideCylinder() and drawCylinder() and cycles through five modes every 2 seconds, putting the mode name in the window title. The order is solid, wireframe, depth buffer disabled, back-face culling, front-face culling.

Things each mode showed.

ModeWhat you see and why

Culling works here only because Chen's winding is consistent. The side triangles (v1, v2, v22) have outward normals and the bottom (v2, v1, v0) has normal \((0,0,-1)\), which also points out of the cylinder. The vertex shader colors each vertex by \(|\text{normalize}(\text{position})|\), so front and back walls landing on the same pixel get different colors, which is what makes the depth and culling modes visible.

Other pieces moved in from Chen's cone class were reshape() with myOrtho(-w/2, w/2, -h/2, h/2, -w, w) to keep the cylinder inside the viewing volume (W7 p.20, W7 p.25), and init(), which enables the depth test once and sets the clear color (W7 p.13). The radius was fixed at w/5 and the depth at 3 (96 triangles) so every 2-second mode shows the whole cylinder. The shaders are Chen's JOGL2_5 shaders with #version 410 for macOS.

Worked example

  1. At depth 3, drawCylinder() allocates 3*4*2^3 = 96 triangles, or 3*3*96 = 864 floats.
  2. Four top-level calls, one per quarter of the circle, each recurse 3 levels to \(2^3 = 8\) wedges. That's 32 wedges in total.
  3. Each wedge writes 3 triangles (bottom, two side halves), \(32\cdot3 = 96\). The draw call is glDrawArrays(GL_TRIANGLES, 0, vBuf.limit()/3), which is \(864/3 = 288\) vertices.

Easy to get wrong

  • "Back-face culling on a closed object changes nothing you can see." True only when the object is closed and the depth test is on. Chen's cylinder is open at the top, so back-face culling opens a visible hole there.
  • "Clear the depth buffer once in init()." Clear it every frame in display(). Enabling the test can be done once (W7 p.13, Lesson 7 video).
  • Chen got confused about the cylinder's array size live in the lecture and his program crashed when he added a top cover without growing the array (Lesson 7 video). If you add triangles to a subdivision, grow the numofTriangle formula to match.

Check yourself

Multiple answer. OpenGL primitives include (a) points (b) lines (c) triangles (d) spheres

(a), (b) and (c). Everything else, including a sphere, is built from those three, which is why only three clipping algorithms are needed (W7 p.4). A sphere is triangles from subdividing an octahedron (W7 p.26).

Multiple answer. A pixel value in the depth buffer means (a) the color or intensity of the model at the pixel (b) if there's no model at the pixel, the distance to the back clipping plane of the viewing volume (c) the closest distance to the viewpoint of the models in the scene at that pixel (d) the distance to a model that may not be at the pixel location

(b) and (c). The depth buffer stores one distance per pixel, the nearest model at that pixel (W7 p.7), and an empty pixel keeps the cleared value, the back plane at 1 by default (W7 p.9). Color is in the color buffer, so (a) is wrong, and (d) talks about a model not at that pixel.

Multiple answer. If you display the depth-buffer image, you can conclude (a) the darker parts are closer to the viewpoint (b) the color-buffer and depth-buffer images both show the visible surface from the viewpoint (c) the depth-buffer image is the same as the color-buffer image but in gray (d) the original 3D model, hidden surfaces included, can be rebuilt from the two images

Per the key, (a), (b) and (c). Near is 0 (dark) and far is 1 (light) (W7 p.9), and the z-buffer test keeps only the nearest surface at each pixel (W7 p.11). That's also why (d) is wrong, since hidden surfaces were never stored. This question was ungraded (0/0) on Quiz 7, and (c) is the shakiest part of the key.

Multiple answer. A normal can be calculated from (a) a surface equation (b) three points (c) two vectors (d) two points

(a), (b) and (c). Two vectors give a cross product, three points give two edge vectors, and a plane equation's coefficients are the normal (textbook 2.3.3). Two points only fix one direction, and a line has infinitely many perpendiculars.

Calculation. A triangle has vertices in order (0,0,0), (2,0,0), (0,3,0). The eye is on the positive z axis. What's its normal, and is it front-facing?

Edges \((2,0,0)\) and \((0,3,0)\). Cross product \((0\cdot0 - 0\cdot3,\ 0\cdot0 - 2\cdot0,\ 2\cdot3 - 0\cdot0) = (0,0,6)\). Dot with \((0,0,1)\) is 6, which is positive, so it's front-facing. The vertices go counterclockwise when seen from +z, which agrees with the right-hand rule (W7 p.14).

Multiple answer. The eye is on the positive z axis. A polygon faces you when (a) the dot product of (0,0,1) and its normal is positive (b) its vertices are counterclockwise from the viewpoint (c) its normal points toward the viewpoint (d) it's not upside down

(a), (b) and (c). Facing is defined by the normal pointing toward the viewer (W7 p.14), the right-hand rule ties that to counterclockwise order (W7 p.14), and Chen gives the positive dot product test (Lesson 7 video). "Upside down" has nothing to do with it. The real Quiz 7 version was ungraded (0/0).

Multiple choice. Given an octahedron, if we subdivide it twice (depth = 2), how many triangles are displayed? (a) 16 (b) 32 (c) 64 (d) 128

(d) 128. Each level turns 1 triangle into 4, so \(8\cdot4^2 = 128\). 32 is depth 1 (W7 p.26 to 27).

Multiple choice. Given two spheres, how do we know they're colliding? (a) center distance bigger than one of the radii (b) not enough information (c) center distance smaller than the sum of the two radii (d) center distance bigger than the sum of the two radii

(c). If the center distance is less than \(r_1 + r_2\) the spheres overlap. Bigger than the sum means a gap, so (d) is the opposite (textbook 2.3.4, Lesson 7 video). This is the one missed on attempt 1.

Calculation. Sphere A at (5,1,2) with radius 3, sphere B at (1,4,2) with radius 1.5. Do they collide?

Distance \(\sqrt{4^2 + 3^2 + 0^2} = 5\). Sum of radii \(4.5\). Since \(5 > 4.5\), no collision, with a 0.5 gap (W7 p.29).
